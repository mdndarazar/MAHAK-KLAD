# Audit C — Store-credit requirements §18–§25

## §18 — PARTIAL
- evidence: `prisma/schema.prisma:791-803` — `StoreCredit` stores `restrictScope` (`ALL`/`CATEGORY`/`VARIANTS`), category/variant ID JSON, minimum purchase, per-transaction maximum, and customer lock.
- evidence: `src/shared/credit.ts:497-534` — `evaluateEligibility` computes eligible/excluded variants and category ancestry; `src/shared/credit.ts:575-675` — `decideRedeem` rechecks status, expiry, remaining amount, uses, customer, minimum purchase, eligible lines, per-transaction cap, and requested amount.
- evidence: `src/main/services/StoreCreditService.ts:456-493` — backend normally reads invoice items and product/category data from the database; `:922-948` calls `decideRedeem` and rejects before deduction.
- evidence: `src/renderer/src/pages/Pos.tsx:494-509` — POS calls the preview and receives eligibility IDs, but only uses the result for `creditApplied`; no renderer code marks, disables, or annotates eligible/excluded cart rows. The preview payload at `:500-507` also sends `customerId: null` and omits each line’s available `categoryId` (the cart stores it at `:327-340`), so category/customer preview is not faithful to the actual cart/customer.
- evidence: `src/renderer/src/pages/Pos.tsx:1437-1451` — renderer shows only the aggregate credit deduction/remainder, not which goods the credit covers.
- evidence: `src/renderer/src/pages/CreditManagement.tsx:204-206` — issue/bulk forms expose amount, customer picker, duration, uses, and reason only; they do not expose category/product scope, minimum purchase, maximum per transaction, or customer-lock controls. The shared payload builders support such fields, but this renderer never sets them.
- gap: **UI(renderer)** POS does not mark eligible cart items, and the management form cannot issue the §18 restrictions. **BACKEND** `:923-924` falls back to `input.lines` when the invoice has no DB lines; that is a request-supplied path contrary to unconditional backend validation and should be removed or restricted to a pre-invoice preview API. **TEST** existing restriction tests exercise shared logic, not the real service/database path.

## §19 — PARTIAL
- evidence: `src/main/services/SalesService.ts:1064-1081` — return-credit issuance stores `returnId` and `sourceInvoiceId`; `:2628-2640` exchange-credit issuance stores `returnId`, `exchangeInvoiceId`, `sourceInvoiceId`, customer, and issue date.
- evidence: `prisma/schema.prisma:846-851` — the three linkage IDs are persisted on `StoreCredit`; `:866-867` persists `remainderCreditId`.
- evidence: `src/main/services/StoreCreditService.ts:2133-2191` — detail data loads redemptions, audit logs, reminders, batch, and remainder credit; `shapeStoreCredit` also returns linkage IDs at `:369-374` and `:426`.
- evidence: `src/renderer/src/pages/CreditManagement.tsx:215-219` — rendered detail shows code/status/amount/remaining/used/counts/source/expiry, operations, and timeline only. It never renders `returnId`, `exchangeInvoiceId`, `sourceInvoiceId`, receipt numbers, or `remainderCredit`/batch links.
- evidence: `src/main/services/StoreCreditService.ts:551-577` — issue-time rules are resolved from the supplied source; `src/shared/credit.ts:575-675` — redemption uses the row’s persisted expiry/uses fields and does not re-derive or validate an immutable exchange origin.
- gap: **UI(renderer)** exchange/original/return links and remainder link are returned by backend but absent from detail UI. **BACKEND** `source` is a mutable scalar (`schema.prisma:768-770`) with no immutable-origin or source/rule consistency check; changing a `MANUAL` row’s source to `EXCHANGE` leaves the manual row’s more permissive stored duration/uses in place, bypassing exchange rules. The backend must preserve/validate origin and exchange rules independently of a mutable `source`. **TEST** no test references `returnId`, `exchangeInvoiceId`, or `sourceInvoiceId`.

## §21 — PARTIAL
- evidence: `src/main/services/StoreCreditService.ts:867-881,922-982` — backend computes the decision itself, checks the invoice and DB lines, and uses optimistic `updateMany` matching prior `usedAmount`/`usedCount`; a losing concurrent request is rejected.
- evidence: `prisma/schema.prisma:899-901,929-938` — redemption `idempotencyKey` is intended to be unique; `src/main/services/StoreCreditService.ts:888-905` returns the prior result for a prior key.
- evidence: `src/main/services/SalesService.ts:1409-1429` calls redemption inside the sale transaction and passes the server-side invoice total/customer plus an idempotency key.
- evidence: `src/renderer/src/pages/Pos.tsx:621-626` — renderer sends the amount and idempotency key, but backend does not trust the amount; `decideRedeem` does the authoritative calculation.
- evidence: `src/main/services/StoreCreditService.ts:1011-1037` — a concurrent duplicate key that passes the initial lookup can hit the unique constraint only after the credit update/payment work has begun; it is thrown as an error rather than reliably replaying the prior result. It does not intentionally double-deduct on the normal optimistic path, but there is no end-to-end proof of request-level replay under a race.
- gap: **BACKEND** `:923-924` permits request lines when DB lines are empty, leaving an edge path for UI-supplied restriction data. **BACKEND** exchange/source immutability is missing as described in §19. **TEST** no real service/Prisma test sends altered amount/date/uses, races two real redemption calls, or verifies duplicate request replay; acceptance checks are structural only.

## §24 — PARTIAL

- evidence: `src/main/services/StoreCreditService.ts:681-705` — issuance AuditLog is a separate call after record creation; the exposed manual path wraps it in a transaction at `:2317-2323`, and sale paths pass a transaction client, but the exported low-level function itself does not establish atomicity.

- evidence: `src/main/services/StoreCreditService.ts:1137-1139` is stale documentation claiming reversal was not wired, while `src/main/services/SalesService.ts:1115-1121` now calls it for full returns; documentation/code consistency is not fully maintained.
- gap: **BACKEND** make bulk batch creation/code rows/audit atomic or explicitly create a durable failed-batch/audit state before any partial work; do not leave an empty batch on pre-insert failure. **BACKEND** make the low-level issuance/redeem contract transaction-safe rather than relying on each caller. **TEST** add DB-error injection tests for code creation, payment/ledger/audit, and bulk chunks. **ANTI-FRAUD** add source immutability/consistency and no-request-line-fallback checks.
