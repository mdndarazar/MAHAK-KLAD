### مورد ۲ — چک PENDING سقف رزرو نمی‌کند + جایگزینی با نقد (کم‌اهمیت) ✅
- **ریشه:** `SalesService.ts:12793-12800` در `addPayment`:
  ```ts
  debtBefore = await invoiceRemaining(tx, invoiceId, grandTotalNow, receivedTotalOf(priorRows))
  remainingBefore = debtBefore.remaining // فقط CLEARED را می‌شمارد
  overpayAmount = isCheque ? 0 : Math.max(0, amount - remainingBefore)
  if (overpayAmount>0) throw BusinessError('اضافه‌پرداخت در هیچ حالتی مجاز نیست...')
  ```
  `receivedTotalOf` فقط `CLEARED` است (`isReceivedPayment = kind!=CHEQUE || chequeStatus==CLEARED`). `pendingChequeTotal` لحاظ نشده.
- **مثال:** فاکتور ۴۰۰k نسیه → چک ۱۰۰k PENDING → نقد ۴۰۰k الان ACCEPT می‌شود → پس از `setChequeStatus(CLEARED)` جمع ۵۰۰k (۱۰۰k اضافه). ۲۵ سناریو `f7_cheque_debt.js` G2 همین را نشان داد.
- **سیاست مالک (تکمیلی):**
  1. فروشنده با اسکن **بارکد فاکتور** در بخش چک‌ها، چک‌های همان فاکتور را فوری پیدا کند؛ همین اسکن برای **نسیه** هم کار کند (پرداخت‌های نسیهٔ همان فاکتور).
  2. روی هر چک PENDING گزینه **«جایگزینی با نقد»** (یا نقد/کارت) باشد.
  3. فروشنده مبلغ را وارد می‌کند:
     - == مبلغ چک → اوکی → چک همان‌جا void + نقد/کارت ثبت **اتمیک**
     - < مبلغ چک → اخطار «حتما باید قبلش چک جدید برای باقی‌مانده ثبت کنید» (مثلاً ۱۰۰k→۶۰k نقد → باید ۴۰k چک جدید)
     - > سقف (`remaining - pendingOther + chequeAmount`) → رد
  4. پول همان روز به **عدد مرجع آبی** (CashMovement + گزارش شیفت) اضافه شود.
- **سناریوی تست طرح:** نسیه ۴۰۰k→چک۱۰۰k→اسکن بارکد→چک پیدا شود→جایگزینی با نقد ۱۰۰k اوکی/۶۰k اخطار/۱۲۰k رد؛ عدد آبی +۱۰۰k
- **اهمیت:** کم (راه دستی void وجود دارد)

### مورد ۳ — رسید DEBT_REDUCTION اشتباه (متوسط) ✅
- **ریشه:** `PrintService.ts:242`:
  ```ts
  returns: { select: {kind,total,refundMethod,refundAmount,refundStoreCreditAmount} }
  // فاقد exchangeTotal/exchangeDiff/debtReduction/exchangeCreditReversed
  remaining = remainingOf({grandTotal, received:paidTotal, ...debtAdjustmentsOf(returns)}).remaining
  ```
  `debtAdjustmentsOf` برای EXCHANGE به `exchangeDebtReductionOf` نیاز دارد که ۰ می‌بیند → payable ۲۵۰k به‌جای ۱۸۰k → remaining ۲۰۰k به‌جای ۱۳۰k
- **مثال:** نسیه ۲۵۰k + ۵۰k نقد (بدهی ۲۰۰k) → تعویض ۱۰۰k→۳۰k با DEBT_REDUCTION ۷۰k → درست ۱۳۰k، رسید ۲۰۰k (۷۰k اختلاف)
- **چرا کم‌ریسک:** `remainingOf`/`debtAdjustmentsOf` در `SalesService.payments()` و `invoiceDebt.ts` همین ستون‌ها را کامل می‌خوانند و درست است؛ اصلاح فقط `select` از ۵ به ۹ ستون — هیچ فرمول عوض نمی‌شود.

### مورد ۴ — `updatePayment` بدون سقف (متوسط) ✅
- **ریشه:** `SalesService.ts:13122` — `data.amount = input.amount` بدون گارد `overpay`
- **مثال:** ۱M نسیه → ۴۰۰k نقد (مانده ۶۰۰k) → ویرایش به ۱.۵M باید رد (۵۰۰k اضافه، حتی ۱ ریال اضافه ممنوع) ولی الان ACCEPT → `paidTotal 1.5M > grand 1M`
- **محل:** جزئیات فاکتور → پرداخت‌ها → مداد ✏️ → ویرایش مبلغ + رمز مدیر (سیاست: حتی با رمز هم ممنوع)

## سیاست‌های کلیدی مالک (حاکم بر داوری)

- اضافه‌پرداخت **مطلق ممنوع** — حتی با رمز، دلیل، یا «بله ثبت کن» — اختلاف دقیق باید گفته شود و هیچ سندی ساخته نشود.
- چک تا `CLEARED` پول دریافت‌شده نیست؛ در `paidTotal` و `remaining` نیست — ولی **باید سقف نقد را رزرو کند** (مورد ۲).
- اعتبار منقضی/باطل/مصرف‌شده → REJECT با `creditOutcomes` و ثبت بدهی با هویت بدهکار — طراحی عمدی، نه باگ.
- UNSELECTED بدون `refundDecision:'DECLINED'` + `refundNote≥3` → REJECT.
- موجودی منفی مجاز است (فقط هشدار) — جز مسیر مرکزی که باید درست import شود.
- هر اصلاح باید تست‌پذیر با هارنس ایزوله (HARNESS_DIR/DB تازه، snapshot قبل/بعد، DB unchanged برای REJECT) باشد.
