# مثال مبتدیانه — باگ ۵: `methodId` خیالی در ثبت فاکتور

> نشانی: `src/main/services/SalesService.ts:3131` تابع `initialPaymentRows`
> تریاژ: `methodId:99999` با فاکتور ۱٬۰۰۰٬۰۰۰ → قبول شد با `method=null, destination=null` ولی `paidTotal 1,000,000` و وضعیت SETTLED

---

## ۱) قصه: فاکتور نقدیِ معمولی

**مشتری:** عمومی
**کالا:** ۲ قلم — ۶۰۰٬۰۰۰ + ۴۰۰٬۰۰۰ = **۱٬۰۰۰٬۰۰۰ ریال**
**پرداخت:** مشتری ۱٬۰۰۰٬۰۰۰ نقد می‌دهد — فروشنده در پنل فروش روش «نقدی» را انتخاب می‌کند.

در حالت درست:
```
فاکتور #30
  جمع: 1,000,000
  پرداخت: 1,000,000 (روش: نقدی — به صندوق)
  مانده: 0 (تسویه)
  گزارش نقدی: +1,000,000 ✅
```

سیستم باید چک کند: «این روش پرداختی که فرستادی واقعاً در جدول PaymentMethod وجود دارد؟»

## ۲) باگ: روش خیالی هم قبول می‌شود

حالا فرض کن یه برنامه‌نویسِ افزونه، یا یه تماس IPC دستکاری‌شده، یا حتی یه باگ در فرانت بفرستد:

```js
create({
  lines: [{variantId: 101, qty:1, unitPrice:600000}, {variantId:102, qty:1, unitPrice:400000}],
  payments: [{methodId: 99999, amount: 1_000_000}] // 99999 وجود ندارد!
})
```

**انتظار درست:**
```
❌ رد شود: «روش پرداخت پیدا نشد؛ از تنظیمات یک روش فعال کنید.»
هیچ فاکتور، پول یا موجودی ثبت نشود.
```
چون سند مالی با روشِ ناموجود بی‌معناست — بعداً در گزارش «تفکیک به روش پرداخت» و تطبیق صندوق، این ۱٬۰۰۰٬۰۰۰ هوا می‌ماند.

**رفتار فعلی (باگ):**
```
✅ فاکتور ساخته شد — id: 4
   پرداخت: 1,000,000
   methodId: 99999
   method: null (چون پیدا نشد)
   destination: null (چون kind معلوم نیست)
   paidTotal: 1,000,000 — تسویه شد!
```

یعنی فاکتور **تسویه** نشان می‌دهد، پول **شمرده** می‌شود، ولی **روش و مقصد پول نامعلوم** است.

## ۳) چرا فقط اینجا؟ `addPayment` درست است

جالب اینجاست که همین چک در مسیر **وصول بدهی** درست کار می‌کند:

```js
// addPayment — درست
addPayment({invoiceId:20, methodId:99999, amount:100000})
→ ❌ «روش پرداخت پیدا نشد» — رد می‌شود (چون assertPaymentMethodExists دارد)

// create — باگ
create({payments:[{methodId:99999, amount:1000000}]})
→ ✅ قبول — چون فقط چک می‌کند «آیا روش چک است؟ آیا اعتباری است؟» ولی نمی‌پرسد «آیا اصلاً وجود دارد؟»
```

کد `initialPaymentRows`:
```ts
const methods = await tx.paymentMethod.findMany({where:{id:{in:methodIds}}})
// اگر 99999 پیدا نشد، methods.length < methodIds.length ولی خطا نمی‌دهد
if (methods.some(m=>m.key===CHEQUE)) throw...
for (m of methods) assertNotCreditMethodKind(m.kind)
// ❌ هیچ assertPaymentMethodExists وجود ندارد
const kindOf = new Map(methods.map(m=>[m.id, m.kind]))
// kindOf.get(99999) → null → destination=null → می‌نویسد!
```

## ۴) مثال‌های کوچک‌تر

- **۱ ریال هم خیالی = باگ:**
  ```js
  payments:[{methodId:99999, amount:1}]
  → فاکتور 1 ریالی با روش خیالی تسویه می‌شود
  ```

- **ترکیبی:**
  ```js
  payments:[
    {methodId: 1 (نقدی واقعی), amount:600000},
    {methodId: 99999 (خیالی), amount:400000}
  ]
  → جمع 1,000,000 درست، ولی 400k بی‌مقصد
  گزارش نقدی: فقط 600k می‌افتد (یا هیچ‌کدام، بسته به باکت‌بندی) → 400k گم
  ```

- **گزارش چی می‌بیند؟**
  - `reportRows` بر اساس `PaymentMethod.kind` یا `destination` جمع می‌زند
  - پرداخت خیالی نه نقد است نه کارت → در هیچ ستونی نمی‌نشیند → در «جمع فروش» هست ولی در «تفکیک صندوق» نیست → مغایرت ۱٬۰۰۰٬۰۰۰

## ۵) اثرش چیست؟

- **پول گم نمی‌شود** (مبلغ شمرده می‌شود) ولی **روش گم می‌شود** → تطبیق صندوق شب: «فروش ۱M ولی نقد+X کارت+Y=600k → 400k کجاست؟»
- سند مالی بی‌اعتبار می‌شود — حسابرس بگوید «این ۴۰۰k با چه روشی آمده؟» جوابی نیست.
- اگر عمدی باشد، می‌شود با روش خیالی فاکتور را تسویه نشان داد بدون اینکه پول واقعی به صندوق/کارت‌خوان بیاید.

## ۷) درستش چیست؟ (بدون اعمال — فقط برای فهم)

قبل از `return rows.map(...)` در `initialPaymentRows`:

```ts
if (methods.length !== methodIds.length) {
  throw new BusinessError('روش پرداخت پیدا نشد؛ از پنل تنظیمات یک روش پرداخت فعال کنید.')
}
for (const id of methodIds) await assertPaymentMethodExists(tx, id)
```

یا ساده: `if (methodIds.some(id=>!kindOf.has(id))) throw...`

همین چک که در `addPayment:12752` هست باید اینجا هم بیاید.
