## ۲. تست `a107-01` — تقصیر من بود، نه فیکسچر تست

بازبینی حدس زده بود «مشکل فیکسچر تست است، نه منطق محصول». **حدس نزدیک بود ولی ریشه جای دیگری بود:**

خروجی خام `prisma migrate diff` علاوه بر تغییر نوع ستون، یک drift از-قبل-موجود را هم «تعمیر» کرد و بی‌صدا دو چیز دیگر را عوض کرد:

| ستون | قبل | بعد از migration من |
|---|---|---|
| `StoreCredit.updatedAt` | `NOT NULL DEFAULT CURRENT_TIMESTAMP` | `NOT NULL` بدون پیش‌فرض |
| `Payment.createdAt` | nullable، بدون پیش‌فرض | `NOT NULL DEFAULT CURRENT_TIMESTAMP` |

اولی دقیقاً همان چیزی بود که `a107-01` را انداخت: هر `INSERT` خامی که `updatedAt` را ننویسد با `NOT NULL constraint failed` می‌افتد.

این **تغییر رفتار روی دیتابیس مشتری** است، نه مشکل تست. یک migration «تغییر نوع ستون» حق ندارد محدودیت‌های دیتابیس نصب‌های موجود را جابه‌جا کند — و خودم در مرحله ۳ همین قاعده را نوشته بودم (تصمیم S181-D8) ولی این دو مورد از دستم در رفته بودند.

**رفع:** هر دو ستون به حالت قبل برگردانده شدند. حالا migration **فقط** نوع ۸۳ ستون پول را عوض می‌کند.

**محافظ جدید (بخش ۶ تست `fix-s181-bigint-migration.mjs`):** کل اسکیما را قبل و بعد اسنپ‌شات می‌گیرد — هر ستون، پیش‌فرض، کلید خارجی و ایندکس — و تنها تفاوت مجاز `INTEGER → BIGINT` روی فیلدهای فهرست پول است. هر چیز دیگری که تکان بخورد، قرمز می‌شود.

## ۳. کارهای بازی که در این نشست انجام شدند

### الف) 🔴 گیت رمز `BackupService.apply` — بسته شد

تأیید بازبینی درست بود: `apply` هیچ گیتی نداشت. این مخرب‌ترین عملیات کل برنامه است:

- `mode: 'replace'` کل دیتابیس زنده را با یک فایل دلخواه جایگزین می‌کند — هر فاکتور، پرداخت و **هر ردیف AuditLog** یک‌جا ناپدید می‌شود.
- `mode: 'merge'` داده‌ی دلخواه را به دفاتر مالی تزریق می‌کند.

یعنی کوتاه‌ترین مسیر برای پاک کردن ردّ دزدی این بود: یک بکاپ *قبل از* عملیات را «جایگزینی کامل» کن. بکاپ ایمنیِ خودکار هم مانع نبود، چون همان کاربر می‌توانست پاکش کند. کل هدف بند ۴-۳۰ با یک کلیک بی‌رمز دور می‌خورد.

**آنچه انجام شد:**
- `assertPanelPassword(PANEL_KEYS.settings, …)` **قبل از هر عمل جانبی** — قبل از `resolve` فایل، قبل از بکاپ ایمنی، قبل از `$disconnect`، قبل از نوشتن Audit. یعنی یک تلاش ناموفق هیچ اثری جا نمی‌گذارد.
- کلید `settings` انتخاب شد چون در `ALWAYS_LOCKED_PANELS` است؛ حتی با خاموش بودن قفل ماژول‌ها هم رمز لازم دارد. (تست همین را قفل می‌کند، تا اگر روزی از آن فهرست بیرون آمد قرمز شود.)
- **ادغام تا امروز هیچ ردیف Audit مستقلی نداشت** — حالا دارد، با سطح تأییدکننده.
- رابط کاربری: فیلد رمز به دیالوگ بازگردانی اضافه شد و بعد از انصراف پاک می‌شود. (گیتی که UI از آن خبر ندارد، قابلیت را از کار می‌اندازد.)

تست: `fix-s181-backup-apply-gate.mjs` — ۲۲ بررسی.

### ب) 🔴 ممیزی `MergeService` — یک باگ بی‌صدا پیدا شد

```ts
const num = (v: unknown, d = 0): number => {
  const n = typeof v === 'bigint' ? Number(v) : Number(v)   // ← هر دو شاخه یکی!
  return Number.isFinite(n) ? n : d
}
```

کسی ternary را نوشته بود تا `bigint` را جدا مدیریت کند، ولی هر دو طرف همان `Number(v)` بودند. تا وقتی ستون‌ها `Int` بودند بی‌ضرر بود؛ بعد از مهاجرت، `$queryRawUnsafe` روی ستون `BIGINT` مقدار `bigint` می‌دهد و این تابع هر مبلغ بالای `MAX_SAFE_INTEGER` را **بی‌صدا** گرد می‌کرد — وسط عملیاتی که دفاتر مالی را انبوه می‌نویسد.

**آنچه انجام شد:** helper جدید `rial()` که اصلاً از `bigint` خارج نمی‌شود، و **۳۶ فیلد مالی** به آن منتقل شدند. `num()` (که حالا فقط برای شناسه/تعداد است) خارج از محدوده‌ی امن خطا می‌دهد؛ چون ادغام روی یک تراکنش است، خطا یعنی «هیچ‌چیز اضافه نشد».

### ج) همان باگ در `MaintenanceService` — و آنجا خطرناک‌تر بود

دقیقاً همان ternary بی‌اثر، کپی‌شده. تنها مصرف‌کننده‌اش `SUM("grandTotal")` روی کل فاکتورهای قدیمی است — یعنی عددی که مدیر **قبل از پاک کردن همیشگی داده** می‌بیند. ممکن بود مبلغ غلط ببیند و بر اساس آن تصمیم بگیرد. حالا به‌جای عدد غلط، خطای فارسی می‌گیرد.

**محافظ:** بخش ۱ تست `fix-s181-merge-maintenance-bigint.mjs` کل `src/` را می‌گردد تا این الگو هرگز برنگردد — چون *به‌نظر* درست می‌آید و در بازبینی کد راحت رد می‌شود.

### د) ۴۲ مورد `$queryRaw` — شمرده و بررسی شد

واقعاً **۴۳** مورد است. از این تعداد، **فقط یکی** ستون مالی را لمس می‌کند: همان `SUM("grandTotal")` در `MaintenanceService` (رفع شد). بقیه روی شناسه، تاریخ و شمارش کار می‌کنند. `MergeService` که `SELECT *` می‌زند هم جدا رفع شد.

بخش ۵ همان تست این را قفل می‌کند تا کوئری خامِ تازه‌ای بی‌سروصدا روی ستون مالی اضافه نشود.

### ه) فایل `وضعیت-خوشه‌ها.md` — به‌روز شد

درست بود که کهنه بود. سطر خوشه M اصلاح شد و یک هشدار بالای فایل اضافه شد که مرجع اصلی، چنج‌لاگ مرحله ۴ است.

## ۶. یک نکته برای بازبین بعدی

دو خطای این نشست (اسکریپت رگرسیون ناقص، و tsc که اجرا نمی‌شد) هر دو یک ریشه داشتند: **به خروجی یک ابزار اعتماد کردم بدون اینکه ثابت کنم ابزار واقعاً همان کاری را کرده که فکر می‌کردم.**

برای همین دو نگهبان اضافه شد (`check-test-coverage.mjs` و اسنپ‌شات اسکیما در تست migration). ولی یک درس عمومی‌تر هم هست که ارزش گفتن دارد: اگر روزی «۰ خطا» یا «همه سبز» دیدید، اول مطمئن شوید عدد از جایی آمده که واقعاً چیزی را سنجیده است. در این پروژه هر دو بار، خروجیِ «سبز» از یک ابزارِ اجرانشده یا ناقص می‌آمد.
