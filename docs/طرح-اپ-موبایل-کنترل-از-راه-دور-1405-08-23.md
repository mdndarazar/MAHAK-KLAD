# طرح اپ موبایل کنترل از راه دور — MAHAK-KLAD

**تاریخ:** ۱۴۰۵/۰۸/۲۳ · **شاخه:** `arena/76a92283-mahak-klad` · **کد پایه:** `87f4298d`  
**وضعیت:** طرح اولیه — هیچ کدی تغییر نکرده — فقط معماری

> این طرح کاملا **افزودنی** است. منطق هسته (پنل فروش خرد/عمده، بارکد اعتباری، برگشت/تعویض زنجیره‌ای، چک/نسیه/تخفیف، بستن صندوق/تحویل شیفت، عدد آبی، صندوق/شیفت) **مطلقا دست نمی‌خورد**.
>
> **یافته کلاد۱+۲+۳+۴+۵+۶+۷+۸:** ZIP ۱۴۰۵/۰۸/۲۳ واقعا ۱۴۳۶ فایل (۸۰ مدل DB، ۳۳۱ کانال IPC) است. کلاد۸ نکته دقیق داد: `AuditLog.audit()` خطا را می‌بلعد (`catch→console.error`) پس AuditLog تنها منبع عدد آبی نیست — باید **مستقیم `CustodyDiscrepancyCase`/`CashSession`** را هم با SELECT خواند (بدون محاسبه) و Heartbeat hash را روی هر دو `auditId`+`caseId` بست. کلاد۶ باگ حیاتی فاز۲ را کشف کرد: `notePanelUnlocked` به تنهایی فقط ۵۱ `assertPanelUnlocked` + `ManagerGate` را باز می‌کند — نسیه/چک، اصلاح برگشت، بستن نشست دیگران، کارت‌به‌کارت (`StoreCredit:2459`, `CardTransfer:364/516/631`) همچنان رمز می‌خواهند. راه‌حل: **~۳-۱۰ خط نگاه فقط‌خواندنی به `RemoteGrantRegistry` در همان ۳ تابع AuthService** (تنها استثنا — با تایید مالک ✅). کلید آینه باید `(storeId, epoch, auditId)` باشد چون `AuditLog.id` بعد از Restore عقب می‌رود — `dbEpoch` تصادفی کنار `panel-vault.key` (کلاد۷) و هشدار «ری‌استور شد» به OWNER.
>
> **نکته فنی کلاد۳:** برای اینکه فروشنده رمز مدیر را نبیند، سیستم پشت‌پرده یک «مجوز موقت» می‌سازد (شما اصلا نمی‌بینید — فقط برای برنامه‌نویس است).
>
> **تعریف مالک از عدد آبی:** عدد مرجع = جمع مورد انتظار **کشو + کارتخوان** (نه فقط نقد). تسویه نسیه‌های قدیمی (نقدی یا کارتخوان) هم داخل همین عدد می‌آید و مغایرت از روی آن حساب می‌شود — این بخش الان دقیق است و طرح فقط همان عدد را بدون محاسبه مجدد به موبایل می‌آورد.

## ۱. هدف

مدیر بدون حضور در فروشگاه، با موبایل خودش (هر موبایلی، نه فقط یک دستگاه) بتواند:
- گزارش فروش/برگشت/تعویض/چک/نسیه/مغایرت عدد آبی را لحظه‌ای ببیند
- ببیند **عدد مرجع (عدد آبی)** دقیقا چقدر است — یعنی الان باید چقدر پول در **کشو + کارتخوان** باشد (جمع هر دو)؛ حتی اگر نسیه‌ی ماه پیش امروز نقدی یا کارتخوان تسویه شده باشد هم در همین عدد حساب می‌شود؛ مغایرت از روی همین عدد تشخیص داده می‌شود
- **هر ماژول/پنلی که قفل است** (نه فقط نسیه) را از راه دور برای همان درخواست خاص باز کند، بدون اینکه فروشنده رمز مدیر را ببیند
- بعد از کار، با یک دکمه «خروج» دوباره فروشنده پشت سیستم بنشیند

> **نسیه فقط یک مثال بود.** منظور تمام بخش‌هایی است که مدیر برای محدود کردن فروشنده قفل می‌کند (مثلا تخفیف بیش از سقف، فروش نسیه، حذف/ویرایش فاکتور، برگشت بدون دلیل، باز کردن صندوق، و هر قفل دیگری). اگر قفلی باز باشد یا فروشنده همان شیفت رمز آن قفل را داشته باشد، همه چیز مثل الان عادی کار می‌کند — این طرح فقط «باز کردن از راه دور» را اضافه می‌کند.

و این قابلیت آنقدر حرفه‌ای باشد که فروشگاه‌ها MAHAK-KLAD را به خاطر همین انتخاب کنند.

## ۲. اصل طلایی — عدم تداخل

- این طرح **هیچ مسیر فروش/برگشت/تعویض موجود را بازنویسی نمی‌کند**.
- فقط یک **لایه API فقط-خواندنی + یک دستور قفل‌گشایی عمومی (برای تمام قفل‌ها)** اضافه می‌شود.
- فروشنده همچنان با همان Electron کار می‌کند؛ مدیر با موبایل فقط **می‌خواند و مجوز می‌دهد**.

## ۳. معماری کلی (۳ لایه)

```
[ فروشگاه Electron ]  <---sync--->  [ سرور ابری MAHAK ]  <---API--->  [ اپ موبایل مدیر ]
   SQLite محلی              Postgres مرکزی              هر موبایل
   صندوق/شیفت/فاکتور       آینه گزارش + مجوزها          iOS/Android/PWA
```

**چرا سرور ابری وسط؟**
- Electron فروشگاه ممکن است آفلاین باشد یا IP ثابت نداشته باشد
- موبایل‌ها نباید مستقیم به SQLite فروشگاه وصل شوند (امنیت + فیلتر)
- سرور وسط هم push می‌فرستد، هم لاگ می‌کند، هم چند مدیر را مدیریت می‌کند

**جریان داده:**
1. Electron هر ۳۰ ثانیه (یا روی هر رویداد مهم) خلاصه گزارش + وضعیت قفل‌ها را به سرور پوش می‌کند (فقط عدد، نه کل DB)
2. موبایل مدیر با API از سرور می‌خواند
3. دستور «باز کردن قفل X» (مثلا نسیه/تخفیف/حذف) از موبایل → سرور → Electron (polling یا websocket) → فروشنده همان قفل را فعال می‌بیند

## ۴. دسترسی چند مدیره — هر موبایلی + دو مدل ورود (ایده مالک)

**ایده شما (خیلی خوبه — همین رو اضافه کردیم):**
مدیر **دو مدل ورود** داشته باشد:

**ورود اول — نامحسوس (فقط دیدن):**
مدیر با یه لاگین ساده (مثلا PIN کوتاه) وارد می‌شود و **همه چیز را بدون رمز و بدون اینکه فروشنده بفهمد** می‌بیند — داشبورد، گزارشات، عدد آبی، مغایرت، چک‌ها. فروشنده اصلا متوجه نمی‌شود مدیر الان دارد نگاه می‌کند. این حالت فقط خواندنی است و هیچ اثری روی سیستم فروشگاه نمی‌گذارد.

**ورود دوم — مداخله (باز کردن قفل):**
وقتی فروشنده زنگ می‌زند «آقای X آمده نسیه می‌خواهد، قفل را باز کن» — مدیر در همون اپ، دکمه «تایید باز کردن قفل» را می‌زند. اینجا برای امنیت، **یه PIN/رمز تایید دوباره** از مدیر پرسیده می‌شود (نه همون PIN ورود اول، یه PIN جدا برای کارهای حساس). بعد از تایید، دستور به فروشگاه می‌رود و فروشنده فقط «✅ مدیر تایید کرد — [نام قفل] باز شد» را می‌بیند. این ورود دوم کاملا لاگ می‌شود.

> طرح قبلی ما تقریبا همین بود ولی تو بهتر و ساده‌تر گفتی — ما الان همین دو مدلی رو رسمی کردیم.

**پیاده‌سازی چند مدیره (نکات کلاد فاز۳+۷+۸):**
- هر فروشگاه یک `storeId` دارد (مثلا `MAH-1234`)
- **نقش‌ها (۱ تا ۵ نفر کل با مالک):** `OWNER` دقیقا ۱ نفر (همیشه حداقل یکی بماند — حذف آخرین OWNER رد می‌شود) — `MANAGER` تا ۴ نفر (فقط پنل‌های تیک‌خورده) — `VIEWER` (فقط دیدن، صفر تایید). سقف ۵ نفر **شامل دعوت‌های معلق هم** (۴۸ساعت خودکار آزاد — کلاد۸)، دعوت ششم رد می‌شود. انتقال مالکیت فقط با PIN دوم. **نشست کامل `MANAGER`-scope** فقط OWNER (۳۸ نقطه `assertManagerSession` فقط این را می‌پذیرند) — MANAGER نمی‌تواند بسازد (کلاد۷).
- **دعوت بدون پیامک:** مالک «افزودن مدیر» → نقش + تیک پنل‌های مجاز → لینک/QR ۱۰ کاراکتری یک‌بارمصرف ۴۸ساعته (کلاد۸) از واتساپ/بله/حضوری (موبایل فقط برچسب). مهمان یوزر+رمز (+PIN دوم) می‌سازد → `PENDING_OWNER_APPROVAL` تا مالک تایید کند. اتمی با `pg_advisory_xact_lock` + `UNIQUE(store_id, seat_no)` + `CHECK seat_no 1..5` + `UPDATE … RETURNING *` (اولین برنده 409 برای بقیه). حذف با PIN دوم → `REMOVED`/`DISABLED` + ابطال همه نشست‌ها/دستگاه‌ها + `revokeBy(memberId)` (حتی اگر آفلاین باشد بدترین حالت ۱۰/۵ دقیقه). بازیابی: MANAGER از OWNER (کد دعوت تازه)، OWNER از ۱۰ کد بازیابی یک‌بار چاپ + مسیر دسکتاپ QR جفت‌سازی با `assertManagerPassword` (حضور فیزیکی — ساده‌ترین و امن‌ترین بدون پیامک).
- **دسترسی به تفکیک پنل:** `CloudSyncService` کاتالوگ را از خود `LOCKED_PANELS` (panels.ts:227) با `catalogHash` می‌فرستد → `store_lock_catalog` در ابر. پنل جدید خودکار ظاهر می‌شود، پیش‌فرض فقط OWNER. ذخیره `member_panel_acl(member_id, panel_key, allowed)` + `can_money` برای حساس + `view_scope` جدا از `approve_panels` + presetهای «نسیه/تخفیف»، «صندوق/شیفت»، «انبار»، «سفارشی». برچسب `NORMAL` (۱۰ دقیقه) یا `SENSITIVE_MONEY` (۵ دقیقه) — پیش‌فرض ناشناخته `NORMAL` + جدول `panel_tier_rules` قابل تغییر در ابر. **settings مثل بقیه ساده است — `isPanelLockEnabled` قفل است ولی `notePanelUnlocked` کار می‌کند، نوشتن `setPanelLocks` همچنان رمز مدیر می‌خواهد.**
- **دو مدل ورود + نقش:** نامحسوس (فقط دیدن) برای همه ولی VIEWER اصلا مداخله ندارد؛ نامحسوس **هیچ ردی روی دسکتاپ ندارد** (حتی AuditLog — چون نوشتن روی shop.db نشانه است) فقط `server_audit`/`watch_log` در ابر (شفاف برای مالک، نه فروشنده)، `pull-on-demand` بی‌UI و `preload` فقط `invoke` دارد پس push لازم نیست — poll هر ثانیه `managerGateStatus` + `remoteAuth:status` کافی است (کلاد۸). مداخله با PIN دوم (۶ رقم، ۵ اشتباه→۱۵ دقیقه قفل) + ارتقا VIEW→ACT با PIN هر بار + پنجره ۱۰ دقیقه بی‌کاری → Grant/Panic + بنر + AuditLog (`REMOTE_GRANT`/`REMOTE_INTERVENTION`) با `note` JSON. OWNER علاوه بر PANEL می‌تواند `MANAGER`-scope بدهد (۵ دقیقه، بنر قرمز).
- **حضانت نکته کلاد:** حضانت کلا `PANEL_KEY` ندارد (PIN شخصی `CustodyCredential`/`masterOverride:2594`/`verifyPin:782` + `authMethod:'CUSTODY_PIN'`) — پس ۳۷ کلید آن را نمی‌پوشاند. در فاز ۳ فقط «دیدن + هشدار» از Snapshot/ AuditLog (بدون محاسبه)، نوشتن حضانت اگر بخواهی فقط OWNER با نشست کامل ۵ دقیقه — فعلا پیشنهاد کلاد۸: روی دسکتاپ بماند (چون یک تایید همه ۳۸ دروازه را باز می‌کند).

- هر مدیر با یوزر+رمز/PIN لاگین می‌کند (بدون پیامک، ≥۱۰ نویسه، لیست رمز رایج رد) + دستگاه (device_key) + کلید بازیابی ۲۴ کاراکتری OWNER. سقف تلاش + زنجیره هش `server_audit` (`hash_n = H(prev||row)` هر ساعت به دسکتاپ) + رمزنگاری ستونی نام/شماره مشتری با لاگ نمایش برای VIEWER.

## ۵. ورود امن مدیر — دو مدل + فروشنده رمز را نبیند (مهم‌ترین نکته شما)

**سناریوی فعلی در فروشگاه:**
- فروشنده پشت سیستم است، یک قفل فعال است (مثلا نسیه، یا تخفیف ۳۰٪، یا حذف فاکتور)
- مدیر از خانه می‌خواهد همان قفل را برای همان درخواست باز کند

> **نسیه فقط مثال است.** این سناریو برای **تمام قفل‌ها** یکسان است: نسیه، تخفیف بیش از سقف، ویرایش/حذف فاکتور، برگشت بدون دلیل، باز کردن صندوق، بستن شیفت با مغایرت، و هر ماژول دیگری که مدیر قفل کرده. اگر قفلی باز باشد یا فروشنده همان شیفت رمز آن قفل را داشته باشد، مثل الان عادی کار می‌کند و نیازی به درخواست از راه دور نیست.

**راه‌حل امن — دو مرحله‌ای (ایده دو مدل ورود شما):**

*حالت عادی (نامحسوس):* مدیر از قبل با ورود اول داخل اپ هست و همه گزارش‌ها را نامحسوس می‌بیند — فروشنده خبر ندارد.

*وقتی قفل باید باز شود:*
1. فروشنده دکمه «درخواست مجوز» کنار همون قفل را می‌زند → یک **کد ۶ رقمی** روی مانیتور فروشگاه ظاهر می‌شود (مثلا `482 917 — نسیه`)
2. مدیر در موبایل همون کد را می‌بیند — **با چشم تطبیق می‌دهد که اشتباه نزند** → دکمه «تایید» را می‌زند و **رمز خودش را تو موبایل خودش** می‌زند
3. همون لحظه روی صفحه فروشنده می‌نویسد: ✅ «مدیر تایید کرد — قفل باز شد» — **هیچ رمزی نشون داده نمیشه**
4. قفل معمولی ۱۰ دقیقه باز می‌مونه، **کارهای حساس پولی (اعتبار گروهی، کارت‌به‌کارت، حضانت) فقط ۵ دقیقه** — که فروشنده سوءاستفاده نکنه (به درخواست مالک)

> برای برنامه‌نویس: پشت‌پرده به جای فرستادن رمز مدیر، یه مجوز موقت ساخته میشه که فقط همین قفلِ همین فروشنده رو باز می‌کنه (شما و فروشنده اصلا اینو نمی‌بینید — کار فنیه).

## ۷. قابلیت‌های فاز اول (MVP حرفه‌ای)

### الف) داشبورد زنده
- فروش امروز (نقد/کارت/نسیه/چک)
- برگشت/تعویض امروز
- **عدد مرجع (عدد آبی)** = جمع مورد انتظار کشو + کارتخوان (نه فقط نقد کشو) → مغایرت لحظه‌ای روی همین جمع حساب می‌شود؛ این عدد تسویه‌های نسیه‌ی قدیمی (نقدی یا کارتخوان) را هم شامل می‌شود و برای شما حیاتی است — الان درست نشان می‌دهد و طرح آن را دست نمی‌زند، فقط همان را به موبایل می‌آورد
- شیفت فعلی: چه کسی، از کی باز است

### ب) گزارشات
- لیست فاکتورها (فیلتر تاریخ/فروشنده) — فقط خواندنی
- جزئیات هر فاکتور + روش پرداخت
- گزارش چک‌ها (در جریان/پاس شده/برگشت خورده)

### ج) قفل هوشمند عمومی — تمام قفل‌ها (ستاره محصول)
- لیست درخواست‌های باز به تفکیک نوع قفل (نسیه / تخفیف / ویرایش / حذف / صندوق / ...)
- باز کردن قفل برای ۱ درخواست / ۱۰ دقیقه / همان فاکتور — عمومی برای هر ماژول قفل‌شونده
- اگر قفل باز باشد یا فروشنده رمز شیفت را داشته باشد، درخواستی ایجاد نمی‌شود (رفتار فعلی حفظ می‌شود)
- **تنظیمات قفل از راه دور:** مدیر از داخل اپ می‌تواند سیاست هر قفل را عوض کند (مثلا قفل تخفیف را باز کند و بگذارد «تا ۱۰٪ روی کل فاکتور مجاز»، یا کامل ببندد) — فروشنده وقتی برمی‌گردد پشت سیستم، سیاست جدید را فعال می‌بیند (مثلا قبلا تخفیف قفل بود، الان ۱۰٪ باز شده). این با «دور زدن سقف» فرق دارد — سقف همچنان رد قطعیه، فقط سیاست کلّی قابل تغییر است
- لاگ کامل: کی، کدام قفل، برای کی، چقدر، کی بست

### د) نوتیفیکیشن
- پوش داخل اپ + (آپشن) تلگرام: برگشت بزرگ، مغایرت > سقف، هر درخواست قفل (نسیه/تخفیف/...)

## ۸. تکنولوژی پیشنهادی (بدون دست زدن به هسته)

- **سرور:** Node.js + Fastify + Postgres (روی سرور داخل ایران — FCM در ایران ناپایدار، WebSocket)
- **API:** REST + WebSocket (برای دستور لحظه‌ای) + Fallback به SSE/Long-polling اگر فیلتر شد
- **احراز هویت:** JWT کوتاه + Refresh چرخشی + **فقط PIN/رمز ساده مدیر (بدون OTP پیامکی — به درخواست مالک، ورود مدیر هرگز به شارژ پیامک وابسته نیست)** — هر مدیر با یوزر/پس خودش روی هر موبایلی لاگین می‌کند، ساده برای چند مدیره (ابر رمز مدیر دسکتاپ را هرگز نبیند، فقط توکن تایید)
- **اپ موبایل:** **PWA** در فاز اول (یک URL، روی هر موبایلی نصب می‌شود، نیاز به Play Store ندارد) — بعدا Flutter
- **همگام‌سازی فروشگاه (ایده کلاد۳+۴+۵+۶):** بهترین منبع آینه `AuditLog` (۱۵۶+ نقطه append-only) + اسنپ‌شات `CashSession`/`Shift`/`CustodyState` — صفر دست‌زدن به سرویس‌های حساس. SyncAgent **فقط SELECT** (`CloudSyncService` کنار `startWooSyncScheduler`، پشت فلگ، `PRAGMA query_only=ON`) — کلید یکتا `(storeId,epoch,auditId)` + Heartbeat hash + tailHash. **سرور هرگز مستقیم به Electron وصل نشود** (NAT) — Electron WS خروجی نگه دارد. **کد ۶ رقمی راز نیست** — شناسه جفت‌ساز؛ امنیت از لاگین + تطبیق چشمی + امضا (HMAC/Ed25519) + `requestId`/`nonce`/`TTL ۶۰s`. همه مبالغ **ریال string** و تاریخ‌ها **شمسی**. سه کانال: Heartbeat ≤۴KB هر ۳۰ث، event سبک، pull-on-demand (۱ بار در ۱۰ث). صف JSONL حلقه‌ای ۵۰MB + اگر ۳ بار شکست خورد ۵ دقیقه توقف + Agent در `worker_threads` جدا (سقف ۱۲۸MB، backoff) تا هنگ نکند. فقط داده مشتق — هیچ `panelAuth`/`vault.key`/PIN به ابر نرود.
- **گام صفر قبل هر کد (کلاد۳+۴):** تمام دیالوگ‌های رمزگیر را بشماریم + چک WAL بودن SQLite + تایید فرمول دقیق عدد آبی در `CashClose.tsx` — بعضی دیالوگ‌ها «رمز خالی» را رد می‌کنند و باید `PasswordField` اگر مجوز فعال بود خودش مقدار را پر کند. برای push از Main به Renderer هم ۱۰-۲۰ خط افزودنی در `useManagerSession`/`ManagerGate` لازم است (تنها لمس UI — در خط قرمز شما نیست). نشست فعلی بی‌کاری‌محور (۵ دقیقه touch) است — مجوز راه دور **انقضای مطلق** جدا (`RemoteGrantRegistry` با تایمر → `clearPanelScope`) + اسکوپ فقط `PANEL` نه `MANAGER`.

**ایده‌های برتر کلاد۱+۲+۳+۴ که اضافه شد:**
- «نوع قفل» = کلید `PANEL_KEYS` (۳۷ کلید) — فروشگاه `LOCKED_PANELS` را به سرور می‌فرستد تا پنل جدید بدون آپدیت سرور/اپ ظاهر شود (کاتالوگ خودکار — کلاد۴) + هر ماژول جدید خودکار شامل می‌شود
- Number Matching واقعی: کد ۶ رقمی روی **هر دو صفحه** — مدیر باید چشم‌تطبیق + انتخاب کند (نه فقط OK) + QR فقط `requestId` (نه رمز) — جلوگیری از تایید از روی خستگی
- مجوز = `notePanelUnlocked(panel,'PANEL',ownerId)` برای همان پنجره (`explicitOwner` آماده) — اسکوپ فقط `PANEL`؛ همه ۳۷ کلید شامل تنظیمات (به درخواست مالک — ساده باشد)
- باز کردن قفل: معمولی ۱۰ دقیقه، **حساس پولی (اعتبار گروهی/کارت‌به‌کارت/حضانت) ۵ دقیقه** (سوءاستفاده نشود) + انقضای مطلق جدا از TTL ۵ دقیقه‌ای (`RemoteGrantRegistry` → `clearPanelScope`)
- قفل موقت: Grant معتبر `AuthLockout` را نمی‌شکند ولی مجاز می‌ماند (علامت `via:REMOTE` در لاگ)
- Outbox جدا + Heartbeat hash + event + pull-on-demand + سلامت فروشگاه (`lastSeenAt`/نسخه/بکاپ/bridgeDiagnostics) + هشدار هوشمند (مغایرت، خارج‌شیفت، فاصله فیش، برگشت زنجیره‌ای، درخواست مشکوک >۳ بار در ۱۰ دقیقه) + نمای زنده قفل‌ها با شمارش معکوس + Panic بستن همه (کلاد۴)
- کاشی «عدد آبی vs کشو» فقط برای OWNER و فقط وقتی شمارش کور تمام شده (حضانت) — بقیه نقش‌ها فقط تجمیعی می‌بینند
- هرگز `shift:current` نخوان — `shift:status` بخوان چون `current` نشست AUTO می‌سازد (نوشتن!)
- Kill-switch دوگانه: از دسکتاپ (رمز مدیر) و موبایل هر دو می‌شه همگام‌سازی رو خاموش کرد + کلید عمومی ابر در Electron پین (safeStorage) + آفلاین = صف برای snapshot درست ولی **صف ممنوع برای Grant** (مجوز نباید دیر اجرا شود) + `requestId` یک‌بارمصرف + replay با HMAC/nonce/seq
- ورود مدیر **بدون OTP پیامکی** (تصمیم مالک ۱۴۰۵/۰۸/۲۳) — پیامک فقط برای مشتری‌ها می‌ماند و ورود مدیر هرگز به شارژ پیامک گیر نمی‌کند

## ۹. امنیت و انطباق

- تمام ترافیک HTTPS
- رمز مدیر bcrypt روی سرور، هرگز به فروشگاه فرستاده نمی‌شود
- لاگ کامل هر باز کردن قفل (چه کسی، از چه IP، برای چه فاکتوری) در AuditLog موجود (`REMOTE_APPROVAL_REQUESTED/APPROVED/CONSUMED`)
- فروشگاه آفلاین = مسیر قدیمی (رمز روی دسکتاپ) دست‌نخورده می‌ماند — قفل هیچ‌وقت به ابر وابسته نمی‌شود (Fail-safe)
- دامنه قفل هوشمند = **فقط قفل‌های موجود** — «تخفیف بیش از سقف» امروز رد قطعیه و قفل نیست (همین می‌ماند)، «برگشت بدون دلیل/بازکردن صندوق/ویرایش ساده» گیت رمزی جدا ندارند — برای اینا قفل تازه نمی‌سازیم؛ اگر بعدا آپدیت کردیم و قفل جدید آمد، اپ هم همزمان آپدیت می‌شود
- حضانت (تحویل شیفت/صندوق) در فاز ۱و۲ فقط خواندنی (مدیر مغایرت‌ها را می‌بیند)، کنترل کاملش در فاز ۳و۴

## ۱۰. نقشه راه

**فاز ۰ — همین طرح + گام صفر (امروز):** تایید شما + شمارش دیالوگ‌های رمزگیر که «رمز خالی» را رد می‌کنند  
**فاز ۱ — API + PWA فقط-خواندنی (۲ هفته):** Snapshot ≤4KB هر ۳۰ث + Delta درخواستی + سلامت/هشدار + PWA آفلاین (IndexedDB) — بدون هیچ diff در Sales/Shift/Cashbox  
**فاز ۲ — قفل هوشمند با توکن `gt_…` (۱ هفته):** `RemoteGrant.ts` + ۴ if در AuthService + IPC `grant:*` + `PanelRequestButton` — معمولی ۱۰ دقیقه، حساس ۵ دقیقه؛ `PeriodLockService` فعلا ممنوع → فاز بعد  
**فاز ۳ — چند مدیره کامل (۱ هفته):** OWNER ۱ + تا ۴ MANAGER/VIEWER (سقف ۵) — دعوت لینک ۳۲بایت/QR یک‌بارمصرف + `PENDING_OWNER_APPROVAL` + قالب‌های آماده (حسابدار/سرشیفت/انبار/کامل) + کاتالوگ خودکار از `LOCKED_PANELS` + تیک پنل جدا `view_scope`/`approve_panels` + رقابت اتمی (صندلی آخر + تایید همزمان اولین تصمیم برنده) + دو مدل ورود (نامحسوس فقط `server_audit`/`watch_log` بدون رد روی دسکتاپ، مداخله PIN دوم + بنر + AuditLog) + **حضانت فاز۳ فقط مدیر-محور** (`resolveUnresolved`/`reverseDisposition`/`setConfig` با `actorKind=GLOBAL_MANAGER`/`authMethod=REMOTE_GRANT` — PIN کارمند هرگز ابری نمی‌شود) — اگر کلاد۶ قبول نشود ۱۰ خط AuthService باید اضافه شود وگرنه نسیه/چک گیر می‌کند  
**فاز ۴ — تلگرام آپشنال + Panic + پولیش (۱ هفته):** تلگرام فقط ابر (Webhook/رله، تیک خاموش، تایید فقط NORMAL غیرمالی با HMAC callback ۲ دقیقه — حساس/Panic فقط PWA با PIN دوم + متن بدون مبلغ پیش‌فرض)، Panic P1 بستن همه Grantها / P2 توقف تایید تا رمز محلی پشت دستگاه (هیچ‌کدام فروش را قفل نمی‌کند — بدترین آفلاین ≤۱۰ دقیقه) + نمای زنده coalesce (هر ۲ث، ۵ مشترک) + هشدار رویدادمحور + سلامت `tailHash`/`auditWatermark` + JSONL حلقه‌ای + worker جدا + تست `git diff` سفید (whitelist + schema hash + سقف ۲۰ خط + حذف ممنوع)
