# نرم‌افزار فروش و انبارداری (جایگزین محک) — فاز اول

اسکلت کامل پروژه: Electron + React + TypeScript + TailwindCSS (RTL) + SQLite/Prisma.
همه‌چیز آفلاین و روی سیستم فروشگاه اجرا می‌شود.

## راه‌اندازی

```bash
npm install
cp .env.example .env
npm run db:generate                  # تولید Prisma Client
npm run dev                          # اجرای برنامه در حالت توسعه
npm run dist:win                     # ساخت نصاب ویندوز
```

### ساختار دیتابیس: خودکار، در هر دو حالت dev و packaged

هیچ دستور migration دستی لازم نیست. برنامه در هر بار بالا آمدن، migration های
پوشه‌ی `prisma/migrations` را روی فایل `shop.db` اعمال می‌کند
(`src/main/db/migrator.ts` که از `prepareDatabase()` در `src/main/index.ts` صدا زده
می‌شود).

* **دیتابیس موجود** (که از قبل داده دارد و جدول `_prisma_migrations` ندارد):
  migration پایه `0_init` فقط «اعمال‌شده» علامت می‌خورد و اجرا نمی‌شود (baselining،
  معادل `prisma migrate resolve --applied 0_init`). هیچ داده‌ای لمس نمی‌شود و
  migration های بعدی عادی اجرا می‌گردند.
* **نصب جدید**: `0_init` کل ساختار را از صفر می‌سازد.
* اگر migration به هر دلیلی شکست بخورد، یک پیام فارسیِ روشن نشان داده می‌شود و
  برنامه بسته می‌شود — نه کرش خام Prisma وسط ثبت فاکتور.

⚠️ **درس این باگ:** قبلاً migration فقط وقتی `app.isPackaged` بود اجرا می‌شد، پس در
حالت توسعه `schema.prisma` جلو می‌رفت و `shop.db` عقب می‌ماند. نتیجه‌اش خطای
«The column `main.SaleInvoice.deductInventory` does not exist» در ثبت و نمایش
فاکتور بود. برای اضافه کردن فیلد جدید، فقط `schema.prisma` را عوض نکنید؛ همیشه
یک پوشه‌ی migration هم بسازید (`npx prisma migrate dev --name ...` یا دستی داخل
`prisma/migrations/`) تا دیتابیس و کد از هم عقب نمانند.

فایل `prisma/manual/…` دیگر کاربردی ندارد و فقط برای سابقه مانده است.

فونت: فایل‌های Vazirmatn را طبق `resources/fonts/README.txt` اضافه کنید.

## قواعد معماری (رعایتشان مهم است)

1. **هیچ‌کس مستقیم موجودی نمی‌نویسد.** فقط `inventoryService.increase/decrease/setStock`.
   منبع حقیقت موجودی جدول `StockMovement` است؛ `ProductVariant.stock` فقط کش سرعت است.
   (فرم کالا هم موجودی را می‌نویسد، ولی از همین لایه رد می‌شود — نه با نوشتن مستقیم فیلد.)
2. **کسر انبار فروش با `state = PENDING` ثبت می‌شود** و در «تجمیع و انتقال» به `FINAL`
   تبدیل و به رکورد `Consolidation` گره می‌خورد. این همان «مهر تایید نهایی» است.
3. **همه‌ی عملیات مالی اتمیک است**: فاکتور + اقلام + پرداخت + حرکت انبار در یک `$transaction`.
4. **جای خالی فاز دوم (ووکامرس)** فقط این‌هاست و هیچ کد/وابستگی ووکامرسی اضافه نشده:
   - فیلدهای `externalSku`، `woocommerceProductId`، `lastSyncedAt` روی `ProductVariant` (فعلاً null)
   - `IInventoryService` که می‌توان پیاده‌سازی Sync-aware را جایش گذاشت (تنها یک خط تغییر)
5. **renderer هیچ دسترسی به Node یا دیتابیس ندارد**؛ همه‌چیز از `IPC` رد می‌شود.
6. **داخل یک `$transaction` هرگز از کلاینت سراسری `prisma` استفاده نکنید.** همیشه همان `tx`
   پاس داده شود (`audit(tx, …)`، `inventoryService.*(…, tx)`). SQLite تک‌نویسنده است و این
   کار بن‌بستِ تراکنش با خودش و خطای «Transaction already closed» می‌سازد.
   تنظیمات مشترک تراکنش‌ها در `src/main/db/tx.ts` (`TX_OPTIONS`) است.
7. **«راحت باشه، نه سخت‌گیر».** این نرم‌افزار تک‌کاربره و شخصی است: محدودیت‌های ساختاری
   (اتمیک بودن، ثبت `StockMovement`) می‌مانند، ولی محدودیت‌های کاربری فقط آگاه‌سازند.
   هیچ عملیاتی بی‌صدا `throw` نمی‌شود و هیچ فیلدی بی‌دلیل قفل نمی‌ماند؛ جایش
   `ConfirmDialog` با پیام فارسی + دکمه‌ی «بله، انجام بده» می‌آید و با تایید کاربر،
   عملیات تحت هر شرایطی انجام می‌شود (پارامتر `force` در سرویس‌های main).

### جزئیات مرحله‌ی ۳ (کالاها)

فایل‌های افزوده‌شده در `src/renderer/src/components/`:

- `Modal.tsx` — modal پایه‌ی RTL پروژه (بستن با Esc/بک‌دراپ). صفحه‌ی میزبان تا وقتی
  modal باز است hotkeyهایش را با `enabled=false` خاموش می‌کند.
- `ProductFormModal.tsx` — «جدید» (F4) و «ویرایش» (F5): محصول پایه + n واریانت،
  کد و بارکد خودکار (خالی) یا دستی، ابزار تولید ترکیبی سایز × رنگ برای پوشاک. IPC: `product:upsert`.
- `MovementsModal.tsx` — «بازبینی» (F6) و «نمایش گردش کالا»: دفتر `StockMovement` واریانت با
  ستون وضعیت (موقت/قطعی)، شماره‌ی تجمیع، سند مرجع و «موجودی پس از حرکت». IPC: `stock:movements`.
- `CategoryModal.tsx` — ساخت/ویرایش گروه و زیرگروه (دو سطح). IPC: `category:tree`, `category:upsert`.
- `StockAdjustModal.tsx` — «موجودی/انبارگردانی»: فقط اختلاف را به‌عنوان حرکت `ADJUSTMENT` ثبت می‌کند.
  IPC: `stock:adjust`.

بازنویسی `src/renderer/src/pages/Products.tsx`: انتخاب چندتایی (checkbox + انتخاب همه)،
ستون‌های سایز/رنگ، دابل‌کلیک = ویرایش، درخت گروه دو سطحی در ستون کنار، نوار پیام
موفقیت/خطا، و وایرینگ کامل F4/F5/F6/F7. «حذف موارد انتخابی» با تاییدیه‌ی شمارش‌دار و
هشدار موجودی غیرصفر انجام می‌شود و در سرویس هم حذف نرم (`isActive = false`) است.

### دو باگ اصلاح‌شده در main (بدون تغییر معماری)

1. `ProductService.nextCode()` از `prisma` سراسری و «آخرین id» استفاده می‌کرد؛ بنابراین ثبت
   محصولی با چند واریانت در یک `$transaction` برای همه یک کد تولید می‌کرد و به خطای
   unique constraint روی `code` می‌خورد. الان کلاینت تراکنش پاس داده می‌شود و مبنا
   «بیشترین کد عددی» است. برای بارکد هم `nextBarcode()` یکتایی را داخل همان تراکنش چک می‌کند.
2. صفحه‌ی کالاها برای اصلاح موجودی از `window.prompt` استفاده می‌کرد که Electron از آن
   پشتیبانی نمی‌کند (همیشه خطا می‌داد)؛ جایش `StockAdjustModal` آمد.

**تغییر ۱ — «مجموع موجودی» در فرم کالا** (`components/ProductFormModal.tsx`)
فیلد نمایشی (readonly) جدید که `totals.stock` را نشان می‌دهد؛ فقط در حالت ویرایش
(`isEdit`) رندر می‌شود و چون از همان `useMemo` روی `draft.variants` می‌آید، با هر
تغییر ردیف‌ها زنده آپدیت می‌شود. چون ردیف اول grid پر بود (۵+۳+۲+۲=۱۲)، عرض
«توضیح» در حالت ویرایش به `col-span-10` کم شده و فیلد جدید در `col-span-2`
درست زیر «تعداد واریانت» و در همان ستون نشسته است (پس‌زمینه‌ی سبز + بولد).
همان عدد در `tfoot` جدول واریانت‌ها زیر ستون «موجودی» هم تکرار شده است.
(از مرحله ۵ این فرم موجودی را هم می‌نویسد؛ پایین‌تر را ببینید.)

**تغییر ۲ — فاکتور خرید** (`pages/PurchaseInvoice.tsx`، بازنویسی کامل)
دو تب: «ثبت فاکتور» و «فاکتورهای ثبت‌شده».
شماره فاکتور خودکار (`purchase:nextNo`)، تاریخ شمسی پیش‌فرض امروز و قابل تغییر،
انتخاب/ثبت سریع تامین‌کننده، افزودن قلم با جستجو (کد/بارکد/نام) یا بارکدخوان
(`useBarcodeScanner`)، قیمت واحد پیش‌فرض از `purchasePrice` و قابل ویرایش، تخفیف
درصدی یا مبلغی، نوع تسویه (`CASH | CHEQUE | ACCOUNT`)، مبلغ پرداختی با نمایش مانده،
یادداشت، و ریست خودکار فرم برای فاکتور بعدی پس از ذخیره.
لیست فاکتورها فعلاً فقط فیلتر بازه‌ی تاریخ + جزئیات اقلام دارد؛ **کم دارد**: فیلتر
تامین‌کننده، جستجوی شماره فاکتور، ابطال/ویرایش فاکتور و چاپ A4.

**تغییر ۳ — فاکتور فروش عمده** (`pages/SalesInvoice.tsx`، بازنویسی کامل)
`Pos.tsx` دست‌نخورده باقی مانده (فروش خرده). این صفحه مخصوص عمده است:
- ورود کالا هم دستی (کد/بارکد/نام) و هم با بارکدخوان؛ محافظ ۳۵۰ میلی‌ثانیه‌ای جلوی
  ثبت دوباره‌ی یک اسکن را می‌گیرد.
- **سوییچ «کسر از موجودی انبار»** بالای فرم، پیش‌فرض روشن. خاموش که باشد فاکتور و
  اقلام و مبالغ عادی ثبت می‌شوند ولی هیچ `StockMovement` ای ساخته نمی‌شود. این
  انتخاب در سطح هر فاکتور روی `SaleInvoice.deductInventory` ذخیره می‌شود.
- **تخفیف درصدی عمده**: `unitPrice = salePrice × (1 − percent/100)` برای همه‌ی ردیف‌ها،
  با امکان override دستی هر ردیف (دکمه‌ی «بازگشت به درصد سراسری» روی همان ردیف).
  درصد روی `SaleInvoice.wholesaleDiscountPercent` ذخیره می‌شود. در سند، `unitPrice`
  همان قیمت مصوب و تخفیف به‌صورت `discount` ردیف ثبت می‌شود تا گزارش «جمع تخفیف»
  درست بماند.
- خریدار از مدل `Customer` (پیش‌فرض «مشتری عمومی»)، تاریخ شمسی، وضعیت تسویه از
  `PaymentMethod`، مبلغ دریافتی با نمایش مانده، هشدار قرمز روی ردیف‌هایی که تعدادشان
  از موجودی بیشتر است، و تب «فاکتورهای عمده» با فیلتر بازه‌ی تاریخ.
- فاکتورهای این صفحه با `orderType = WHOLESALE` ثبت می‌شوند تا از فیش‌های POS جدا باشند.

**تغییرات main (سرویس‌ها)**
- `SalesService.create`: پارامترهای `deductInventory`، `wholesaleDiscountPercent`،
  `issuedAtJalali` و `orderType = WHOLESALE`. وقتی `deductInventory === false` است
  مرحله‌ی `inventoryService.decrease` کلاً skip می‌شود؛ بقیه‌ی فاکتور عادی ثبت می‌شود.
  همه‌چیز داخل همان `$transaction` قبلی است و `AuditLog` با اکشن
  `WHOLESALE_SALE_CREATE` و یادداشت «با/بدون کسر از موجودی انبار» ثبت می‌شود.
- `SalesService.createReturn`: برگشتِ فاکتوری که بدون کسر موجودی ثبت شده بود، موجودی
  را زیاد نمی‌کند (تقارن حسابداری؛ وگرنه انبار الکی پر می‌شد).
- `PurchaseService.create`: اعتبارسنجی اقلام، تاریخ شمسی دلخواه، `userId` در AuditLog،
  کلاینت تراکنش در `nextInvoiceNo` و `PurchaseService.get`. افزایش موجودی همچنان فقط
  از طریق `InventoryService` و داخل یک `$transaction`.
- `PartyService.ts` (جدید): جستجو و ثبت سریع مشتری/تامین‌کننده با کد خودکار
  (مشتری از ۱۰۰۰، تامین‌کننده از ۲۰۰۰) + AuditLog. کانال‌های جدید:
  `customer:list`, `customer:create`, `supplier:list`, `supplier:create`
  (این همان قلم «باقی‌مانده‌ی شناخته‌شده» بخش قبلی README بود و بدون آن انتخاب
  تامین‌کننده/خریدار ممکن نبود).
- `shared/jalali.ts`: `jalaliToday`, `toLatinDigits`, `isValidJalaliDate`,
  `jalaliToDateTime`, `jalaliStartOfDay`, `jalaliEndOfDay`.
- `shared/enums.ts`: `OrderType` (با `WHOLESALE`)، `SettlementType` + برچسب‌های فارسی،

## مرحله ۵ — رفع باگ تراکنش + اصل «محدودیت غیرمسدودکننده»

### ۱) باگ بحرانی «Transaction API error: Transaction already closed»

**ریشه:** `AuditService.audit()` همیشه با کلاینت سراسری `prisma` می‌نوشت، ولی از داخل
`prisma.$transaction(async (tx) => …)`ِ باز صدا زده می‌شد. SQLite در هر لحظه فقط یک
نویسنده می‌پذیرد ⇒ نوشتن لاگ منتظر آزاد شدن قفلِ تراکنش می‌ماند و تراکنش هم منتظر تمام
شدن همان `await audit(...)` ⇒ بن‌بست با خودش و انقضای تراکنش پس از ۵۰۰۰ms.

**اصلاح:**

- امضای تابع: `audit(client, input)` — کلاینت آرگومان اول و اجباری است
  (`audit(tx, …)` داخل تراکنش، `audit(prisma, …)` بیرون آن).
- همه‌ی صدا‌زدن‌ها اصلاح شد: `ProductService` (PRICE_EDIT با `tx` · DELETE با `prisma`)،
  `PurchaseService`، `SalesService` (دو نقطه)، `CashboxService` (CASH_CLOSE با `prisma` ·
  CONSOLIDATE با `tx`)، `InventoryService` (`tx ?? prisma`)، `PartyService` (دو نقطه).
- **دو مورد اضافه که در جستجوی کامل پیدا شد:**
  1. `InventoryService.finalizePending()` با کلاینت سراسری `updateMany` می‌زد، در حالی که
     از داخل تراکنش `CashboxService.finalize` صدا زده می‌شد (همان باگ، در «تجمیع و انتقال»).
     الان `tx` می‌گیرد.
  2. `SalesService.nextReceiptNo()` با کلاینت سراسری داخل تراکنش می‌خواند؛ الان `tx`
     می‌گیرد (هم ریسک بلاک، هم ندیدن نوشته‌های همان تراکنش).
- `getStock`/`setStock` هم پارامتر اختیاری `tx` گرفتند تا از داخل تراکنش قابل استفاده باشند.
- **لایه‌ی ایمنی:** `src/main/db/tx.ts` → `TX_OPTIONS = { timeout: 15000, maxWait: 5000 }`
  روی همه‌ی ۶ تراکنش main.

### ۱) باگ «رمز پیش‌فرض تنظیمات عوض نشد» — `AuthService.ts` + `shared/receipt.ts`

**ریشه:** `DEFAULT_MANAGER_PASSWORD` از قبل `'1111'` بود، ولی رمز پیش‌فرض بارِ اولی که

**اصلاح:** `LEGACY_DEFAULT_MANAGER_PASSWORDS` (فعلاً `['13431374']`) + تابع

انجام می‌شود تا کاربر لازم نباشد اول یک بار رمز اشتباه بزند.

### ۳) برداشت خودکار از انبار مرکزی هنگام کمبود موجودی فروشگاه

- تنظیم `SaleDefaults.autoCentralWithdraw` (پیش‌فرض **خاموش**) + چک‌باکس کنار «تخفیف
  فاکتور» در پنل فروش تکی. تیک همان لحظه ذخیره می‌شود، پس با بستن برنامه پاک نمی‌شود.
- `secondaryStockService.coverShortage(client, lines, opts)`: کمبود هر قلم

- تطبیق کالا (چون انبار مرکزی عمداً هیچ کلید خارجی ندارد) متنی و اولویت‌دار است:

  می‌شود.
- هشدار **زرد**: در پنل فروش دو جا — همان لحظه‌ی اسکن/انتخاب کالا (پیش‌بینی) و بعد از

  `centralWithdrawals` و `centralWithdrawnQty` هم هست.
- **تیک خاموش = رفتار قبلی مو‌به‌مو**: `coverShortage` اصلاً صدا زده نمی‌شود، موجودی
  منفی می‌شود و همان هشدار قبلی می‌آید. رفتار خودِ پنل انبار مرکزی هم تغییر نکرده.
- همه‌چیز داخل همان `$transaction` ثبت فاکتور و با پاس دادن `tx` (قاعده‌ی ۶ README).

### ۴) دکمه‌ی «نمایش کالاهای انبار فروشگاه» در پنل انبار مرکزی

استفاده می‌کند، پس تا وقتی سوییچ روشن است شماره‌ی شیفت **هرگز** پشت‌سرهم زیاد نمی‌شود.
یک نکته‌ی ظریف هم اصلاح شد: رکورد بسته فقط وقتی دوباره باز می‌شود که ساعت جاری
*واقعاً* داخل بازه‌ی همان شیفت باشد؛ در حالت «خارج از بازه» صندوقی که بسته‌اید بسته
می‌ماند. `ShiftInfo` سه فیلد نمایشی گرفت (`byTime`، `windowLabel`، `outsideWindow`) و
پنل بستن صندوق برچسب «شیفت بر اساس ساعت · بازه · خارج از بازه‌های تعریف‌شده» را نشان
می‌دهد. سوییچ خاموش = رفتار خودکار قبلی، دست‌نخورده.

### ۷) هشدارهای پنل فروش تکی روی فاکتور فروش عمده

`SalesInvoice.tsx`: همان چک‌باکس «برداشت خودکار از انبار مرکزی» (یک تنظیم مشترک بین دو
پنل)، هشدار زرد کمبود موجودی *قبل* از ذخیره با جزئیات هر قلم، و نمایش
`stockWarnings` برگشتی از main بعد از ثبت/ویرایش. متن قدیمی و نادرست «ذخیره با پیام
موجودی کافی نیست رد می‌شود» هم اصلاح شد (از مرحله‌ی ۵ به بعد کمبود موجودی هیچ‌وقت
مانع ثبت نیست). `salesService.update` هم همان مسیر `coverShortage` را برای *اختلاف*
اقلام دارد.

### ۸) خروجی اکسل «بانک شماره مشتریان»

دکمه‌ی «خروجی اکسل (xlsx)» در تب مشتریانِ تنظیمات، از همان مسیر خروجی گزارش‌ها
(`system:exportExcel` ← `ExportService` ← نویسنده‌ی OOXML در `services/xlsx.ts`). پس
فایل یک xlsx واقعی و سالم است (ستون‌بندی درست، سرستون ثابت، مبالغ به‌صورت عدد، برگه‌ی
راست‌به‌چپ) و مسیر ذخیره را خود کاربر انتخاب می‌کند. ستون‌ها: کد، نام، شماره تلفن،
تعداد فاکتور، جمع خرید، آخرین خرید، تاریخ ثبت + ردیف جمع. فیلترهای بالای جدول
(جستجو و «فقط دارای شماره») روی خروجی هم اعمال می‌شوند. هیچ کتابخانه‌ی جدیدی نصب نشد.


## مرحله ۱۲ — هفت مورد درخواستی (قفل چک‌باکس، جمع تخفیف، مدیریت مشتریان، باگ شیفت، هشدارها، جدول عمده)

### ۱) قفل چک‌باکس «برداشت خودکار از انبار مرکزی» + همگام‌سازی سه‌پنلی

`hooks/useAutoCentralWithdraw.ts` (جدید) تنها مالک این گزینه است: مقدار همان
`sale.autoCentralWithdraw` روی جدول `Setting` می‌ماند (بدون migration) و سه پنل — پنل
فروش تکی، فاکتور فروش عمده و **تنظیمات انبار مرکزی** (کادر جدید بالای پنل انبار مرکزی) —
همان یک مقدار را می‌خوانند و می‌نویسند. تغییرش فقط با «نشست مدیر» ممکن است (`disabled` +
پیام فارسی برای کارمند). همگام‌سازی زنده با رویداد `mahak:settings-changed` انجام می‌شود
که `useSettings` به آن گوش می‌دهد، پس هر پنلِ باز همان لحظه وضعیت جدید را نشان می‌دهد.
رفتار خود برداشت خودکار (سمت main) دست‌نخورده است.

### ۲) «جمع کل تخفیف‌ها» و «جمع پس از تخفیف» در گزارشات فروش

`SalesReports.tsx`: یک ردیف زردِ اضافه در `tfoot` هر دو تب (سرجمع و جزئیات) و برای هر
گروه شیفت، به‌علاوه‌ی جمع ستون تخفیف سر جای خودِ ستون در تب جزئیات. سرجمع: جمع مبلغ کالا
منهای جمع تخفیف · جزئیات: (قیمت واحد × تعداد) منهای جمع تخفیف. همان دو عدد به چاپ حرارتی
و نوار پایین صفحه هم اضافه شد. هیچ محاسبه‌ی سمت main عوض نشده است.

### ۳) مدیریت دستی مشتریان + جلوگیری از رکورد تکراری

`Customer` دو ستون گرفت (migration `20261101000000_…`): `isWholesale` و
`manualPurchaseTotal` (هر دو با پیش‌فرض، پس داده‌ی موجود لمس نمی‌شود). `PartyService`:
`updateCustomer`، `deleteCustomer` (با `force` و انتقال فاکتورها به «مشتری عمومی» —
قاعده‌ی ۷)، و `directory` با فیلتر نوع و «حداقل جمع خرید» برای قرعه‌کشی. جمع خرید نمایشی
= جمع فاکتورها + مبلغ دستی. تب مشتریانِ تنظیمات: فرم ثبت/ویرایش، حذف با تایید، ویرایش
مبلغ خرید در همان ردیف، و تغییر نوع با یک کلیک.
**رکورد تکراری:** `findCustomerByPhone` شماره را با تحمل قالب (۰۹۱۲…/۹۸۹۱۲…/۹۱۲…) تطبیق
می‌دهد و `resolveCustomer` سمت فروش از همان استفاده می‌کند، پس خرید بعدیِ همان شماره —
حتی ۱۲ ماه بعد — به همان مشتری وصل و فقط «تعداد فاکتور» او زیاد می‌شود.

### ۴) باگ تشخیص شیفت هنگام «تعیین شیفت بر اساس ساعت»

ریشه‌ی باگ: بستن صندوق، شیفت را از «شیفت *بازِ* امروز» (یا از شناسه‌ای که پنل لحظه‌ی باز
شدن خوانده بود) می‌گرفت، نه از ساعت. اگر شیفت صبح (۰۸–۱۴) بسته نشده بود، بستن صندوق ساعت
۱۶ با نام «شیفت صبح» ثبت می‌شد. اصلاح: `shiftService.shiftForNow` / `byTimeEnabled` و
`cashboxService.close` که در حالت زمان‌بندی ساعتی همیشه شیفتِ شامل *ساعت بستن صندوق* را
انتخاب می‌کند (مگر کاربر صریحاً شیفتی را از فیلتر انتخاب کرده باشد: `explicitShift`)؛
`shiftService.close` بدون شناسه هم همان مسیر را دارد. سمت UI: شیفت هر دقیقه و یک بار
دیگر *در لحظه‌ی بستن صندوق* تازه می‌شود و نام شیفت ثبت‌شده در پیام موفقیت دیده می‌شود.
⚠️ با خاموش بودن چک‌باکس، شماره‌گذاری خودکار و پشت‌سرهم قبلی (تا شیفت ۱۰) دست‌نخورده است.

### ۵) دکمه‌ی «فهمیدم» روی هشدار زرد کمبود موجودی (فاکتور عمده)

`SalesInvoice.tsx`: هشدار با «فهمیدم» بسته می‌شود، ولی «امضای کمبود» (قلم/تعداد/موجودی)
نگه داشته می‌شود؛ پس با هر تغییر واقعی در کمبود، هشدار دوباره می‌آید و هیچ هشداری بی‌صدا
پنهان نمی‌ماند.

### ۶) جدا‌سازی مشتریان عمده از تکی در جستجوی خریدارِ پنل عمده

`PartyPicker` پارامتر `scope` گرفت. پنل عمده با `scope="wholesale"` فقط مشتریان عمده
(به‌علاوه‌ی «مشتری عمومی») را نشان می‌دهد و «ثبت سریع خریدار جدید» همان‌جا مشتری را با
برچسب «عمده» ذخیره می‌کند. اگر شماره‌اش از قبل به‌عنوان مشتری تکی ثبت شده باشد، رکورد دوم
ساخته نمی‌شود و همان مشتری برچسب «عمده» می‌گیرد. در تب مشتریانِ تنظیمات، ستون «نوع» با
برچسب عمده/تکی/عمومی و فیلتر سه‌حالته اضافه شد.

### ۷) ارتفاع جدول اقلام فاکتور فروش عمده

جدول اقلام از `flex-1` تنها به `flex-1 min-h-[300px] max-h-[52vh] overflow-auto` با
سرستون چسبان (`sticky`) تغییر کرد، پس هم در ثبت فاکتور جدید و هم در ویرایش فاکتور قبلی،
همه‌ی ردیف‌ها با اسکرول کامل دیده می‌شوند.


## مرحله ۱۳ — هشت مورد درخواستی (حذف تک‌فاکتوری، باگ فیلتر مشتری، کلید چاپ، قفل عوارض، لیبل، بکاپ، کد فاکتور عمده)

### ۱) حذف تک‌فاکتوری در پنل «حذف گزارشات فروش»

`SalesService.purgePreview` / `purge` یک ورودی اختیاری `invoiceIds` گرفتند و `purgeStockPlan` هم
همان فهرست را می‌پذیرد. خالی بودنش = همان حذف بازه‌ای قبلی، مو‌به‌مو. پرشدنش = فقط همان فاکتورها
(بازه‌ی تاریخی نقشی ندارد) با *همان* تراکنش، همان پرسش «موجودی‌ها به انبار بازگردند؟»، همان
محاسبه‌ی «فروخته منهای برگشت‌خورده» و همان ثبت در AuditLog. سمت UI: یک ستون چک‌باکس کنار هر ردیف
(+ تیک «همه»)، دکمه‌ی «حذف n فاکتور انتخاب‌شده»، و مودال پرسش که برای انتخاب، شماره فیش‌ها و
تعداد بازگشتی همان انتخاب را نشان می‌دهد. بعد از حذف انتخابی، فهرست همان بازه دوباره خوانده می‌شود.

### ۲) باگ فیلتر «نوع مشتری» (لیست خالی می‌شد)

دو ریشه داشت و هر دو برطرف شد: (الف) سمت UI، `setCustomerKind` و `loadCustomers` با
`setTimeout` صدا زده می‌شدند، پس *مقدار قبلی* فیلتر به سرور می‌رفت؛ حالا نوع انتخاب‌شده صریح
پاس داده می‌شود (`loadCustomers(k)`). (ب) سمت main، فیلتر روی ستون `isWholesale` در where کوئری
بود و روی داده‌ای که این ستون در آن NULL است (ستون بعداً اضافه شده / ادغام بکاپ قدیمی) نه با
`= 0` می‌خورد و نه با `= 1` ⇒ فهرست خالی. حالا `directory` فیلتر نوع را در حافظه اعمال می‌کند
(`matchesKind`، NULL = تکی). **هیچ‌جای این مسیر چیزی حذف نمی‌کرد و نمی‌کند**؛ فیلتر فقط نمایش را
محدود می‌کند و متن حالت خالی هم همین را می‌گوید.

### ۳) چک‌باکس «چاپ فاکتور» در پنل فروش تکی

`sale.printEnabled` (پیش‌فرض روشن = رفتار فعلی) به `SaleDefaults` اضافه شد و چک‌باکسش در پنل
فروش، *همان لحظه* ذخیره می‌شود. خاموش که باشد نه چاپ خودکار انجام می‌شود و نه چاپ دستی (دکمه‌ی
چاپ هم جایش پیام «چاپ خاموش است» می‌آید). ثبت فاکتور، کد برگشت و آمدنش در گزارشات فروش در هر دو
حالت دست‌نخورده است؛ این تیک فقط روی «چاپ» اثر دارد.

### ۴) قفل رمزی پنل «عوارض و مالیات» و «حق سرویس»

در `main.tsx` هر شش مسیر `charges/*` داخل `ChargesGate` (همان `ManagerGate`) قرار گرفتند، با همان
رمز و همان «نشست مدیر» پنل تنظیمات/کالاها/فاکتور خرید. یک بار ورود مدیر، همه را تا «خروج مدیر»
باز می‌کند و کارمند به هیچ‌کدام دسترسی ندارد.

### ۵ و ۸) تنظیمات و چاپگر مستقل «چاپ لیبل»

کلید تنظیمات جدید `label.template` (`LabelTemplate` در `shared/receipt.ts`) با پیش‌فرض لیبل
۵ سانتی‌متر طول × ۳ سانتی‌متر عرض: چاپگر مخصوص لیبل (جدا از چاپگر فاکتور)، طول/عرض، ارتفاع بارکد،
فونت اسم و قیمت، و چک‌باکس‌های «اسم کالا چاپ شود / قیمت / کد کالا / ارقام بارکد / چاپ بی‌درنگ».
`labelHtml` بازنویسی شد: هر لیبل یک صفحه به اندازه‌ی خودِ لیبل (`@page size`)، پس دستگاه
برچسب‌زن هر لیبل را روی یک برچسب چاپ می‌کند. کانال `print:labels` چاپگر و ابعاد را از همین کلید
می‌خواند (`deviceName`) و `LabelPrintModal` پیش‌نمایش را با همان ابعاد می‌سازد و حالت سوم
«بدون اسم» گرفت. تنظیمات چاپ فاکتور مطلقاً لمس نشده است.

### ۶) مسیر و بازه‌ی بکاپ خودکار

کلید `backup.config` (`BackupConfig`): `autoDir` (خالی = پوشه‌ی داخلی برنامه)، `everyDays`
(۰ = خاموش)، `keep`، و `lastAutoAt`. `runBackup({ scheduled: true })` بازه را رعایت می‌کند و
زمان‌بند هر ۶ ساعت *بررسی* می‌کند؛ بکاپ دستی و بکاپ قبل از پاک‌سازی همیشه گرفته می‌شوند. اگر
مسیر انتخابی در دسترس نباشد (فلش جدا شده)، بی‌صدا به پوشه‌ی داخلی برمی‌گردد تا بکاپ هیچ‌وقت
متوقف نشود. پنل «بکاپ و بازگردانی»: انتخاب مسیر با پنجره‌ی ویندوز، عدد بازه و تعداد نسخه، و
دکمه‌ی «بکاپ فوری». فهرست بکاپ‌ها هر دو پوشه را نشان می‌دهد.

### ۷) کد فاکتور و مهلت برگشت برای فاکتور فروش عمده

چهار تنظیم مستقل: `wholesaleReturnCode` (پیش‌فرض روشن)، `wholesaleReturnCodeDays`،
`wholesaleReturnCodeDaysRemote`، `wholesaleReturnCodeLength`. در `SalesService.create` شرط
`withCode` از «فقط غیر عمده» به «عمده هم، طبق تنظیم خودش» تغییر کرد و مهلت/طول کد از اعداد همان
اسکوپ خوانده می‌شود؛ پس رسید فاکتور عمده هم کد + بارکد + تاریخ اعتبار چاپ می‌کند و
`sale:byReturnCode` (پنل برگشت از فروش) بدون هیچ تغییری آن را پیدا می‌کند. فاکتور عمده‌ای که از
قبل بدون کد ثبت شده، با اولین ویرایش کد می‌گیرد (کد فاکتورهای دارای کد هیچ‌وقت عوض نمی‌شود). در
پنل فاکتور فروش عمده هم چک‌باکس «مشتری راه دور» اضافه شد و کد صادرشده در پیام موفقیت دیده می‌شود.

## افزودن ماژول جدید: چک‌لیست

> این بخش از سرِ `src/shared/panels.ts` به اینجا منتقل شده است (نشست چهارم) و
> **قرارداد رسمی و همیشگی این پروژه** است، نه یک مورد استثنایی. هر توسعه‌دهنده‌ی
> بعدی — چه انسان، چه یک مدل هوش مصنوعی — باید بدون این‌که صاحب نرم‌افزار دوباره
> بخواهد، آن را رعایت کند.

هر قابلیت / ماژول / صفحه / حتی هر **گزینه‌ی حساسِ** جدیدی که از این به بعد به این
نرم‌افزار اضافه می‌شود، **باید** امکان تعریف «رمز دوم اختصاصی» داشته باشد، دقیقاً
با همین الگو و همین چهار قدم:

1. یک کلید جدید در `PANEL_KEYS` (`src/shared/panels.ts`).
2. یک ردیف جدید در `LOCKED_PANELS` (عنوان فارسی + یک خط توضیح این‌که رمزش به چه
   کسی داده می‌شود).
3. پوشاندن آن صفحه/کامپوننت با `<ManagerGate panel={PANEL_KEYS.xxx} title=… reason=… />`
   (برای قفل کردن یک تب یا یک چک‌باکس داخل یک پنل، از `inline` استفاده کنید).
4. تست با **رمز مدیر**، با **رمز دوم**، و **بدون هیچ رمز**.

> **جلسه ۵۵ — یک نکته‌ی عملی از کار ۱:** اگر یک کارِ حساس *داخل* یک ماژول دیگر
> است (مثل «ساخت کالای جدید هنگام انتقال از انبار مرکزی»)، **قفل آن ماژول را قرض
> نگیرید**. قرض گرفتن قفل `products` برای این کار یعنی انباردار برای ساخت یک کالا
> مجبور بود رمز پنل کالاها را بگیرد و همراهش *حذف کالا، تغییر قیمت و ورود موجودی*
> هم برایش باز می‌شد. قاعده: هر کارِ حساس، کلید مستقل خودش
> (`secondaryToStoreNewProduct`) — همان چهار قدم بالا، با یک ردیف تازه در
> `LOCKED_PANELS` و یک `hint` که صریح بگوید این رمز چه چیزی را باز می‌کند و چه
> چیزی را **نمی‌کند**.

همین چهار قدم کافی است: پنل «تنظیمات → رمز دوم اختصاصی پنل‌ها» خودش روی
`LOCKED_PANELS` حلقه می‌زند، پس ردیف جدید بدون هیچ کد اضافه‌ای در تنظیمات ظاهر
می‌شود و مدیر می‌تواند همان‌جا رمز دومش را بگذارد یا حذف کند.

### دو قاعده‌ی ثابت و بدون استثنا

1. **رمز مدیر همیشه همه‌ی این قفل‌ها را باز می‌کند**، چه رمز دوم برایشان تعریف
   شده باشد چه نشده باشد. مدیر همه‌کاره است.
2. تا وقتی برای یک پنل رمز دوم تعریف و فعال نشده، رفتار همان قبل است: فقط رمز
   مدیر بازش می‌کند (پس «رمز دوم» همیشه اختیاری است، پیش‌فرض خاموش).

ورود با «رمز دوم» فقط همان یک پنل را باز می‌کند و «نشست مدیر» نمی‌سازد، پس کارمندِ
آن بخش به بقیه‌ی پنل‌ها دسترسی پیدا نمی‌کند.

### قفل موقت (بخش ۲)

بعد از چند بار رمز اشتباه پشت‌سرهم (پیش‌فرض ۳ بار)، *همان* گیت برای مدت
تنظیم‌شده (پیش‌فرض ۱۰ دقیقه) قفل می‌شود و تا پایان آن مدت **حتی رمز درست هم
پذیرفته نمی‌شود**. شمارنده و زمان قفل در دیتابیس (جدول `AuthLockout`) نگه داشته
می‌شوند، پس بستن و باز کردن برنامه قفل را دور نمی‌زند. منطقش در
`src/main/services/AuthService.ts` است، تنظیماتش در «تنظیمات → مدیریت → رمز و
امنیت»، و شمارش معکوسش روی خودِ `ManagerGate` نشان داده می‌شود.

هر نقطه‌ی ورود رمز یک **گیت مستقل** است: رمز اشتباه زدن روی پنل کالاها نباید بستن
صندوق را هم قفل کند. صفحه‌ی ورود رمز مدیر گیت مخصوص خودش را دارد (`__manager__`).

## نشست ۵ — بازبینی و تکمیل پرامپت «رمز دوم، قفل موقت، تعویض کالا، نسیه»

کل پرامپت بازبینی شد. بخش‌های ۱ تا ۸ از قبل پیاده شده بودند؛ این سه مورد جا افتاده بود و در این نشست کامل شد:

1. **بخش ۶ — بارکد اعتبار روی «فاکتور فروش عمده»:** پرامپت خواسته بود اسکن بارکد اعتبار «در پنل فروش *و فاکتور فروش عمده، برای یکدستی*» باشد. زیرساختش (`CreateSaleInput.storeCreditCode`) آماده بود ولی صفحه‌ی `SalesInvoice.tsx` هیچ ورودی‌ای نداشت. اضافه شد: فیلد اسکن/تایپ + دکمه‌ی «بررسی» + بررسی خودکار، نمایش مبلغ کم‌شده، و بازگشت باقی‌ماندهٔ اعتبار. در حالت *ویرایش* عمداً غیرفعال است تا یک اعتبار دو بار خرج نشود.
2. **بخش ۶ — باگ مصرف اعتبار:** سقف جذب اعتبار سمت main «باقی‌ماندهٔ فاکتور» است، ولی پنل فروش کل مبلغ را نقد می‌فرستاد ⇒ باقی‌مانده صفر و کل فاکتور با خطا برمی‌گشت. حالا `cashDue = قابل پرداخت − اعتبار` مبنای پرداختی است و روی صفحه هم به‌صورت «نقد قابل دریافت» دیده می‌شود (هر دو صفحه).
3. **بخش ۳ — ساعت در دو جای جامانده:** جدول «تجمیع و انتقال» (ستون ساعت قطعی‌شدن) و پیام «این شیفت قبلاً بسته شده» که فقط تاریخ را می‌گفت.

## نشست ۶ — بازبینی کامل پرامپت هشت‌بندی (قفل ماژولار، تخفیف، تغییر قیمت گروهی، گزارش‌ها، انبار فروشگاه)

### تکمیل بند ۵ برای ماژول «تنظیمات» (تنها موردِ جامانده)

ریشه‌ی مشکل: صفحه‌ی تنظیمات از قاعده‌ی بند ۵ جا مانده بود و هنوز ساختار قدیمی
داشت: ریشه `h-full`، شبکه‌ی دو ستونی `flex-1 overflow-hidden`، پنل محتوا
`overflow-auto`، و جدول‌هایش داخل کادرهای `max-h-[45vh..60vh] overflow-auto`.
نتیجه‌اش همان چیزی بود که بند ۵ برای حذفش نوشته شد: جدول «قفل ماژول‌ها» (۲۱
ردیف)، «مشتریان»، «بکاپ‌ها» و «حذف گزارشات فروش» در یک پنجره‌ی کوچک فشرده
می‌شدند و چرخ ماوس گاهی صفحه را می‌چرخاند و گاهی کادر داخلی را (اسکرول تودرتو).

تغییرها (فقط چیدمان؛ هیچ منطق یا تنظیمی لمس نشده است):

- `Settings.tsx`: ریشه از `flex flex-col gap-2 h-full` به کلاس مشترک `page`،
  شبکه از `flex-1 overflow-hidden` به `items-start`، و `overflow-auto` پنل محتوا
  برداشته شد. پس کل صفحه به قدِ محتوایش باز می‌شود و با چرخ ماوس اسکرول می‌شود.
- نوار بالای تنظیمات `sticky top-0 z-30` شد تا دکمه‌ی «ذخیره‌ی تنظیمات» و تب‌ها
  در جدول‌های بلند هم همیشه در دید بمانند.
- کلاس جدید `.tbl-wrap` در `styles.css` (`border + rounded + overflow-x-auto`)
  جای هشت کادر `max-h-… overflow-auto` را گرفت: هیچ سقف ارتفاعی نیست (جدول کامل
  باز می‌شود) و فقط اسکرول *افقی* برای جدول‌های پرستون می‌ماند.
- ستون «پیش‌نمایش زنده‌ی رسید» چون دیگر قدِ پنجره نیست، `xl:sticky xl:top-16` شد
  و پیش‌نمایش سقف `max-h-[70vh]` گرفت تا در صفحه‌ی بلندِ تنظیمات همراه چشم بماند.

ناحیه‌های «کاری» (سبد پنل فروش، سبد برگشت/تعویض، سبد فاکتور عمده) مثل قبل عمداً
دست‌نخورده‌اند: آن‌ها گزارش نیستند و باید کنار فرم پرداخت در یک صفحه جا شوند.

### دو نکته که عمداً تغییر نکرد (نیازمند تصمیم مالک نرم‌افزار)

1. **override دستی عوارض/حق سرویس در «فاکتور فروش عمده»** هنوز هست. بند ۲ پرامپت
   صریحاً «پنل فروش» را گفته بود و آن انجام شده؛ پنل عمده خودش قفل رمز دارد و
   معمولاً دست مدیر است. اگر می‌خواهید آن‌جا هم فقط‌خواندنی شود، یک خط تغییر است.
2. **سیاست تخفیف (بند ۳) فقط سمت UI اعمال می‌شود** (`Pos.tsx`)، نه داخل
   `SalesService`. برای یک برنامه‌ی دسکتاپ تک‌کاربره کافی است و عمداً سخت‌گیر
   نشد تا ویرایش فاکتورهای قدیمی‌تر (که با سیاست قبلی تخفیف خورده‌اند) با خطا
   نخورد. اگر بخواهید، می‌توان یک بازبینی سمت main هم اضافه کرد که تخفیف
   خارج از سیاست را در `AuditLog` علامت بزند (بدون بستن مسیر ثبت فاکتور).
