# پرامپ کامل — کمپین تست منطقی MAHAK-KLAD (برای کلاد)

> این فایل را همراه ZIP سورس پروژه به کلاد بده. متن زیر دقیقاً همان چیزی است که باید اجرا شود.

---

## ۰) نقش تو

تو **ممیّز منطق مالی** یک نرم‌افزار فروشگاه (MAHAK-KLAD) هستی، نه توسعه‌دهنده. کار تو در این مرحله فقط **کشف باگ منطقی** و **تولید گزارش** است. هیچ خطی از کد محصول تغییر نمی‌کند.

## ۱) قواعد آهنین (نقض هرکدام = خروجی بی‌اعتبار)

1. **هیچ تغییری در `src/`، `prisma/` و `tests/` موجود نده.** فقط فایل‌های تازه در پوشهٔ `/tmp/...` برای تست بنویس.
2. **هیچ اتصالی به دیتابیس واقعی/استیجینگ نکن.** هر سناریو روی **SQLite موقت و ایزوله** با پوشهٔ تازه.
3. **هر ادعا قبل از ثبت، با اجرا اثبات شود.** حدس، «به‌نظر می‌رسد» و «احتمالاً» ممنوع.
4. **هیچ شکستی را «پاس» اعلام نکن.** و هیچ پاس شدنی را با تخفیف‌دادن معیار، پاس نکن.
5. اگر سناریویی به‌خاطر محدودیت محیط قابل اجرا نبود، در بخش **«اجرا نشده»** با دلیل بنویس؛ در شمار پاس‌ها نیاور.
6. معیار درستی، **سیاست مالک (مالک محصول)** است، نه رفتار فعلی کد. رفتار فعلی فقط «واقعیت» است که با سیاست سنجیده می‌شود.
7. هیچ داده، فایل گزارش یا ZIP در مخزن بازنویسی نکن؛ خروجی‌ها بیرون از مخزن بمانند.

## ۲) دامنهٔ محصول

| محور | محدودهٔ تست |
|---|---|
| پنل فروش خرد | فاکتور یک‌قلمی تا **۳۰ قلم** |
| پنل فروش عمده | فاکتور یک‌قلمی تا **۵۰۰ قلم** |
| پرداخت | نقد، کارت، ترکیبی نقد+کارت، نسیه (بدهی)، چک، ترکیب نسیه+چک+نقد+کارت |
| تخفیف | تخفیف قلم، تخفیف فاکتور، تخفیف درصدی/مبلغی، تخفیف مدیر، **تخفیف تاریخی و انتقال آن در تعویض (سه گزینه NO / YES / YES_ZERO)** |
| برگشت | جزئی، کامل، چندباره روی یک فاکتور، برگشت پس از برگشت |
| تعویض | ساده، با مابه‌التفاوت مثبت/منفی/صفر، نقد، کارت، اعتبار، کاهش بدهی (`DEBT_REDUCTION`)، ترکیب نقد+کارت با ماندهٔ اعتباری |
| زنجیره | تعویض روی تعویض، برگشت روی فاکتور سوم و چهارم (`فاکتور → تعویض → تعویض → برگشت`) |
| بارکد اعتباری | `ALL` (همه‌کالا)، مخصوص یک کالا، مخصوص یک یا چند دسته، چند بارکد در یک فاکتور **حداکثر ۸ عدد**، ترکیب `ALL` + کالا + دسته در یک فاکتور، مصرف جزئی/کامل، انقضا، مصرف‌شده، باطل‌شده |
| تاریخ | فاکتور با تاریخ گذشته، **بازهٔ مجاز برگشت/تعویض**، فاکتور **منقضی** (باید رد شود)، تعویض با تاریخ گذشته |

### استثنای مهم (خواستهٔ صریح مالک)
برای فاکتورهای **نسیه / چک / ترکیب آن‌ها با نقد و کارت** فقط **مرحلهٔ اول** تست شود:
خرید یک یا چند قلم در یک فاکتور ← برگشت / چند تعویض ساده / برگشت ساده، در حالت‌های مختلف.
**زنجیره (تعویض روی تعویض، برگشت روی فاکتور سوم و چهارم) برای این فاکتورها لازم نیست.**

## ۳) آنچه باید پوشش داده شود (همه، نه نمونه)

- همهٔ روش‌های بازپرداخت: نقد، کارت، کارت‌به‌کارت، اعتبار خرید، «بدون بازپرداخت با دلیل»، کاهش بدهی.
- انتخاب‌نشده (`UNSELECTED`) باید **پیش از هر نوشتن** متوقف شود (برگشت، پرداخت، انبار، اعتبار: هیچ‌کدام).
- منع اضافه‌پرداخت: فروش، ویرایش فاکتور، وصول بدهی، برگشت — با **اختلاف دقیق ریالی** در پیام و بدون نوشتن.
- منع بازپرداخت بیشتر از حق واقعی؛ منع برگشت بیشتر از باقی‌ماندهٔ قابل‌برگشت.
- سقف اعتبار/مصرف اعتبار، اعتبار منبع‌دار در تعویض (بازگشت سهم اعتبار به منبع)، اعتبار `ALL` و محدود.
- بدهی: `remaining` باید در فاکتور، گزارش، دفتر و رسید **یک عدد** باشد.
- انبار: کالای برگشت‌خورده/تعویض‌شده، زیان، انبار مرکزی، FEFO.
- چک: جایگزینی چک (مبلغ دقیق `selected + D` فقط یک‌بار، بدون ±۱، اتمیک، فقط `PENDING`/`BOUNCED`)، وضعیت‌های چک.
- تخفیف: سقف، انتقال در تعویض، عدم دوباره‌شماری در سود و زیان.

## ۴) ردِ منطقی در برابر شکست (مهم‌ترین بخش داوری)

خیلی از «رد شدن‌ها» **درست و منطقی** هستند و **نباید شکست شمرده شوند**. برای هر رد شدن، سه چیز را ثبت کن: (۱) پیام دقیق، (۲) اینکه دیتابیس **بی‌تغییر** مانده، (۳) دلیلی که ثابت می‌کند این رد با سیاست مالک سازگار است.

نمونه‌های «رد منطقی» (لیست کامل نیست؛ خودت موارد بیشتر پیدا کن):

| سناریو | چرا رد، درست است |
|---|---|
| تعویض کالایی که قبلاً برگشت خورده | آن کالا دیگر در فاکتور نیست |
| مصرف دوبارهٔ بارکد اعتباری مصرف‌شده | اعتبار یک‌بارمصرف است |
| بارکد منقضی | طبق سیاست مدت اعتبار |
| برگشت روی فاکتور منقضی (خارج از بازهٔ مجاز) | سیاست بازه |
| بازپرداخت بیشتر از حق واقعی | ضدسرقت |
| پرداخت بیشتر از فاکتور / بدهی | منع اضافه‌پرداخت |
| تعویض با روش تسویهٔ انتخاب‌نشده | تصمیم ثبت‌نشده |
| جایگزینی چکِ پاس‌شده | چک پاس‌شده برگشت‌پذیر نیست |
| برگشت بیشتر از باقی‌مانده | سیاست |

**اگر سیستمی این‌ها را قبول کرد، آن «شکست واقعی» است.**

## ۵) روش اجرا

1. از هارنس موجود پروژه استفاده کن: `node --import ./test/harness/register.mjs <script>` با `HARNESS_DIR`/`HARNESS_DB` تازه برای هر سناریو.
2. هر سناریو: ساخت داده → اجرای عملیات → ثبت خروجی سرویس → پرس‌وجوی مستقیم SQLite برای اثبات اثر (یا عدم اثر) → ذخیره در JSON.
3. برای ردها، **snapshot قبل/بعد** بگیر و برابری را اثبات کن.
4. برای سناریوهای زنجیره‌ای، شمارهٔ فاکتور/تعویض هر گام را نگه دار تا قابل بازتولید باشد.
5. هر باگ مشکوک را **دو بار** اجرا کن (تازگی داده) تا از deterministic بودن مطمئن شوی.
6. حجم: حداقل چند صد سناریوی مستقل؛ برای ماتریس‌ها (۲ قلم × ۵ روش × ۳ نوع تخفیف …) از تولید ترکیبی استفاده کن و شمار پیکربندی‌های **یکتا** را گزارش بده.

## ۶) قالب گزارش نهایی (دقیقاً همین)

```
## جمع‌بندی
- سناریوهای اجراشده: N
- پاس: P
- ردِ منطقی (درست): R
- شکست واقعی (ناسازگار با سیاست مالک): F
- اجرا نشده (با دلیل): S

## باگ‌های ناسازگار با سیاست مالک (به ترتیب شدت)
| # | عنوان | سیاست نقض‌شده | فایل:خط | سناریوی بازتولید | اثر پولی (ریال) | وضعیت |
```

و برای هر باگ: گام‌های بازتولید، خروجی واقعی، خروجی مورد انتظار طبق سیاست، و اینکه آیا پول واقعی جابه‌جا شده یا فقط گزارش غلط است.

## ۷) ممنوعیت‌های صریح

- تغییر کد محصول یا تست‌های موجود.
- «اصلاح» کد برای سبز شدن سناریو.
- حذف/بازنویسی گزارش‌های موجود.
- اعلام پاس برای سناریویی که اجرا نشده.
- محدود کردن ماتریس به «چند نمونه» — باید همهٔ حالت‌های ممکن هر محور ترکیب شود.

## ۸) تحویل

یک فایل گزارش Markdown + یک فایل JSON خام سناریوها + فهرست تست‌های تازه (بیرون از مخزن). در پایان فقط بگو: «N سناریو، P پاس، R رد منطقی، F شکست، S اجرا نشده».
